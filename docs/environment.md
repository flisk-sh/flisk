# Environment, params and secrets

Three different things reach a container's environment, and they live in three different places.

| What | Where you write it | Committed? | How it reaches the container |
| --- | --- | --- | --- |
| Project settings and generated credentials | the project `.env` (or the file `flisk up --env-file` selects for one run) | No (gitignored) | Docker Compose reads it for `${NAME}` interpolation |
| Non-secret config | `params` in `service.json` | Yes | A generated `.env.backend.autogenerated` file |
| Secret values | the project `.env`, named in `secrets` in `service.json` | Only the names | Injected by Compose from the project `.env` |

Nothing secret is ever written to a generated file. Generated files are checked by `flisk config verify` and are meant to be committed.

## The project `.env`

`flisk project` creates it with working defaults. `flisk up` (and a repeat `flisk project`) adds any key a newer CLI expects to an older
`.env` and **never changes a value that is already there**, so an existing `DB_PASSWORD` is not rotated.

| Key | Purpose |
| --- | --- |
| `TILT_ENV` | Tilt environment name (`dev`) |
| `DB_PASSWORD` | The Postgres password. Generated per project (32 hex characters). |
| `DATABASE_URL` | A connection string built from the same `DB_PASSWORD`. Compose sets the `DATABASE_URL` of each backend itself. |
| `JWT_SECRET` | Signs `local-jwt` tokens. Generated per project (64 hex characters), never shared between projects. |
| `VERDACCIO_URL_DOCKER`, `VERDACCIO_URL` | Only used by Verdaccio, a premium feature. Not required. |

The project `.env` parser follows the Compose-compatible subset used by this CLI: `export NAME=value` works; unquoted inline
comments are stripped only when `#` is preceded by whitespace; quoted values end at their matching quote and ignore the rest of the
line. Double-quoted values decode `\n`, `\r`, `\t`, `\"`, `\\`, and `\$`. Single-quoted values remain literal, with `\'` accepted for an
embedded quote. Variable interpolation, colon separators, and multiline values are not implemented here; Compose remains responsible for container interpolation. `NAME=""` and `NAME=''` count as empty.
`flisk doctor` reports a missing required key, an empty one, and a `DATABASE_URL` whose password differs from `DB_PASSWORD`.

## Another env file for one run

`flisk up --env-file <path>` runs the stack with a different project env file. It is opt-in: without the option the project `.env` is the
env file of the run, exactly as before.

```bash
flisk up --env-file .env.integration
```

The selected file **replaces** the project `.env` for that run. It is not merged with it, and the project `.env` is neither read nor
completed for that run: Flisk does not add the keys it generates to a file the run ignores.

Rules:

- A relative path is resolved against the current directory, the way `docker compose --env-file` and
  Node.js' own `--env-file` resolve it. Run `flisk up` from the project directory (the usual case), so
  `.env.integration` names the file next to `.env`.
- The file has to live **inside the project**. The wake gateway mounts the project read-only and runs
  Compose itself, so it can only read a file inside it. A path outside the project is refused.
- The file must exist, be a file, and be readable. A missing or unreadable file stops the run before
  anything starts, with a message that names the path.
- The file must carry the same keys the platform needs: `TILT_ENV`, `DB_PASSWORD` and `JWT_SECRET`. A
  file that misses one is refused, and the message names the **key**, never a value. Flisk does not
  complete the file: a file you name may well be committed, and writing a generated credential into
  it would leak one.
- A project whose vendored engine predates the option is refused with the fix (`flisk config
  regenerate`), because the old engine would ignore the selection silently.
- A stack that is already running keeps the env file it started with, so the option is refused
  (exit code `1`) instead of being ignored. Run `flisk down` first, or pass `--force` to replace the
  running stack.
- Values are never printed. The output names the file (`Using env file: .env.integration`), never a
  value, and the values of the selected file are masked in smoke-check output just like the ones in
  the project `.env`.
- `--env-file` is the only way to select the file. `TDK_ENV_FILE` is the variable the CLI uses to
  hand the file to the engine, and an inherited value is ignored, so a run without the option always
  uses the project `.env`.

On a Node.js-based installation (the npm package), Node.js reads `--env-file` as one of its own
options before Flisk starts: it checks that the file exists, relative to the current directory, and
reports a missing file itself (`node: .env.integration: not found`). Every other check above is
Flisk's own.

### Precedence

Inside one container, Docker Compose resolves a value in this order:

1. **The compose `environment:` entry** of the service. It carries the generated values (`PORT`, `DATABASE_URL`, `NODE_ENV`) and
   the secrets of the env file of the run (`JWT_SECRET`, every name in `secrets`).
2. **The service-level env file** - the generated `.autogenerated/.env.<type>.autogenerated`, written from the `params` of
   `service.json`. It holds non-secret config only.

The values inside the compose `environment:` entry come from the **env file of the run** - the project `.env`, or the file
`--env-file` selected. It is the source of `JWT_SECRET`, `DB_PASSWORD`, the `DATABASE_URL` built from it, and every secret a
`service.json` names. The engine loads it into the Tilt environment *and* hands it to Compose as the interpolation env file, so the
same values reach every service of the stack.

For the keys the env file of the run defines, its value wins over the value exported in your shell: the engine loads the file into the
Tilt environment, and Compose prefers the environment of the process over the `--env-file` it is given. A key the env file does not
define keeps the value from the shell - including the host ports Flisk picks for the run (`TDK_HTTP_PORT`, `TDK_HTTPS_PORT`,
`TDK_POSTGRES_PORT`, `TDK_BIND_ADDRESS`), which the env file of the run can override in turn.

So a `param` in `service.json` and a key in the env file of the run are two different things: the `param` wins for its own key (it is
the only source for it), and the env file of the run wins for the keys Compose injects (`JWT_SECRET`, the secrets, the database
password).

### A repeatable integration run

Keep the integration configuration next to the project `.env`, and give it the same keys:

```bash
# 1. One-time: copy the project credentials, then change what differs.
cp .env .env.integration
printf '\nAPI_BASE_URL=https://staging.example.test\nFEATURE_FLAGS=beta\n' >> .env.integration

# 2. Every integration run: the same command, the same file.
flisk up --env-file .env.integration

# 3. Back to the local configuration.
flisk up
```

The copy is what makes the run repeatable: the file carries the per-project credentials (`DB_PASSWORD`, `JWT_SECRET`), so the stack
starts with the same database password as the local run and the same signed tokens.

Two things to know before you use it in CI:

- The flag needs no terminal, no prompt and no answer: it works the same in a pipeline as in a shell. `flisk up --env-file
  .env.integration --json` reports the run in the usual JSON envelope.
- A different `DB_PASSWORD` does not change the local database: the Postgres volume keeps the password it was created with, so the
  database may refuse the new one. `flisk up --env-file` warns when the selected file sets another `DB_PASSWORD` than the project
  `.env`.

## Params

`params` in `service.json` are non-secret strings written to the resource's generated env file. A plain value stays bare; a value
containing a space, `#`, `$`, a quote, a backslash or a newline (or an empty value) is double-quoted with those characters escaped, so
the file stays valid dotenv:

```json
{ "params": { "PLAIN": "ok", "GREETING": "hello world", "NOTE": "a # b", "PRICE": "$5" } }
```

```text
PLAIN=ok
GREETING="hello world"
NOTE="a # b"
PRICE="$$5"
```

`$` is written as `$$` because Docker Compose expands `$NAME` and `${NAME}` in env files: an unescaped dollar would silently pick up
some other variable. In a real container, `"price $$FOO"` arrives as the literal `price $FOO`.

`envVars` is the deprecated name for `params`. It is still read when `params` is absent, so older manifests keep working, and
`flisk doctor` warns: `service.json.envVars: deprecated, use params (still read when params is absent)`. The same goes for
`dependencies`, the deprecated name for `dependsOn`.

## Secrets

List the names a resource needs; keep the values in the project `.env`:

```json
{ "secrets": { "required": ["STRIPE_KEY"], "optional": ["SENTRY_DSN"] } }
```

```text
# .env (gitignored)
STRIPE_KEY=sk_test_...
```

- A **required** name is injected as `${NAME:?...}`: Docker Compose refuses to start the resource and says which name is missing.
- An **optional** name is injected as `${NAME:-}`: the resource starts with the variable empty.
- Names must be valid environment variable names (letters, digits and underscores, not starting with a digit); anything else fails
  with the resource and the name in the message.
- `TDK_SECRET_PROVIDER=infisical` (set in the environment) leaves secrets to Infisical, and nothing is injected from `.env`.

## Auth

A backend defaults to `AUTH_MODE=local-jwt`, and Compose requires `JWT_SECRET` from the project `.env`:

```text
JWT_SECRET is not set. Run `flisk up` (it adds a generated one to the project .env) or add JWT_SECRET to .env
```

With `dependsOn` containing `identity`, or with `"authMode": "identity-service"`, the mode is `identity-service`,
`IDENTITY_RESOURCE_URL` is set, and `JWT_SECRET` is neither set nor required for that service.

`identityServiceUrl` in `service.json` sets that URL, and the generated env file and the Compose entry both use it. (Compose used to
read only the deprecated `envVars.IDENTITY_RESOURCE_URL`, so setting `identityServiceUrl` left Compose on the default.) That deprecated
`params` / `envVars` entry is still honoured when `identityServiceUrl` is absent, and `identityServiceUrl` wins when both are set. With
neither, the default is `http://identity-service:3000`, which is a guess: services listen on their own port, not 3000, so set
`identityServiceUrl` to the real URL.

`jwtSecret` in `service.json` is **ignored**, and `flisk doctor` warns about it (`service.json.jwtSecret: ignored. A secret must not be
committed: ...`). It is also left out of the generated `.autogenerated/service.yaml` mirror, so the generated files never copy it. Set
`JWT_SECRET` in `.env` instead. The old shared default `local-development-secret-min-32-chars-long` is gone.

## Prisma

A backend gets a Prisma `DATABASE_URL` in its generated env file only when `prisma` is in `featuresEnabled` (or `usePrisma` is
`true`), the same rule the Dockerfile generator uses.

## What was checked, and what was not

Checked through a real `flisk up` in an isolated project: the generated file says `AUTH_MODE=local-jwt` and carries no `JWT_SECRET`;
quoted params arrive correctly in the container (`GREETING=hello world`); the container's `JWT_SECRET` and `STRIPE_KEY` come from the
project `.env`; an optional secret arrives empty; Docker Compose refuses to start with the messages above when a required secret or
`JWT_SECRET` is missing; and `flisk up` adds a missing `JWT_SECRET` to an older `.env` without touching `DB_PASSWORD`.

Checked for the alternate env file (`flisk up --env-file`) in an isolated project with a real `flisk up`: the Postgres container came up
with the `DB_PASSWORD` of the selected file, and a run without the option came up with the `DB_PASSWORD` of the project `.env`; the
output named the selected file and no value; a missing file, a file outside the project and a file without `JWT_SECRET` were all
refused before anything started.

Not checked or not changed:

- How Tilt displays Compose's missing-secret error. Only Compose itself was observed.
- `.autogenerated/service.yaml` still mirrors the rest of `service.json`. Only `jwtSecret` is left out of it, so any other secret a
  person types into a manifest field would still be copied there.
- The Infisical provider itself (this change only stops injecting from `.env` when it is selected). Its older generator
  (`secrets_generator.star`: fixed secret names, port 8089 in one place and 8080 in another, `INFISICAL_ALLOW_FALLBACK` true in one
  helper and false in the other) is not on the default path: `use_infisical` defaults to false and nothing in the free engine passes
  true. It is still loaded by the Docker layer files, which now say so, and it was not changed.
- Dependency URLs: only frontends get `VITE_<NAME>_API_URL`; backends get none for `dependsOn`, and `API_URL` is built from the stack
  rather than the resource name, so two backends in one stack share it.
- Python backends receive the same generated env file as Bun backends.
- `dependencies` and `envVars` are warned about but still read. They are not removed yet; that is a later, announced change.
- The alternate env file was checked with the shared infrastructure (Postgres). A service with a `params` block was not run, and the
  wake gateway (which starts a deferred service with Compose itself) was not exercised either.
