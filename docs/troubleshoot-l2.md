# Troubleshooting: L2 (dependency layer) Docker build failures

This guide covers failures in **L2**, the dependency resolution and package caching layer of TDK's Docker image stack. It explains what L2 caches, how dependency manifest inputs and `CACHE_BUSTER` control cache invalidation, and how to diagnose and resolve errors when package installation fails or cache invalidation does not behave as expected.

Outputs on this page were captured on a developer workstation running macOS with Docker Desktop 29.8.2 and Bun 1.3.11. In Case 3A, the symptom, the build-toolchain fix and the `ldd` check were run; the `gcompat` fix and the glibc `Exec format error` variant were not. Package counts, step numbers, durations and timestamps vary by project and machine.

---

## What L2 is in plain words

In TDK's four-tier Docker image hierarchy (L1–L4), **L2** is the dependency layer:

| Layer | Name | Purpose | What it contains | Defined in |
|---|---|---|---|---|
| **L1** | Base OS & Runtime | Foundational OS & runtime | Alpine Linux, Bun runtime (`oven/bun:1.3.11-alpine`), essential utilities (`curl`, `bash`, `openssl`), and system user `app`. | [`l1_base_layers.star`](../engine/topologies/platform/docker/layers/l1_base_layers.star) |
| **L2** | **Dependencies** | **Package resolver & module cache** | **Installed `node_modules/`, workspace hoisted packages (`.bun`), and package manager cache mounts (`/cache/bun`).** | [`l2_dependency_layers.star`](../engine/topologies/platform/docker/layers/l2_dependency_layers.star) |
| **L3** | Builder | Compilation & asset building | Service compilation, Prisma CLI, frontend bundler, and production pruning. | [`l3_builder_layers.star`](../engine/topologies/platform/docker/layers/l3_builder_layers.star) |
| **L4** | Runtime | Final production/dev container | Lean runtime (Bun for backends, Nginx or Bun static for frontends, migrator). | [`l4_runtime_layers.star`](../engine/topologies/platform/docker/layers/l4_runtime_layers.star) |

### What L2 caches

L2 isolates slow, network-bound package downloads and disk-heavy dependency trees (`node_modules`) from fast application code changes. Specifically, L2 caches:
1. **Per-service `node_modules/`:** The resolved package directory under `/app/<service>/node_modules`.
2. **Monorepo / hoisted modules:** The shared hoisted directory `/app/node_modules/.bun` used by Bun's isolated linker.
3. **Download cache:** Pre-warmed package tarballs stored in `/cache/bun` (via Docker BuildKit cache mounts: `--mount=type=cache,target=/cache/bun,sharing=shared`).

### How L2 layer caching and invalidation works

Docker builds use a content-addressable cache. Each instruction in a Dockerfile creates a layer keyed on the hash of the instruction and its inputs:

```
[L1: Base Image] (oven/bun:1.3.11-alpine)
       ↓
[L2: ARG CACHE_BUSTER]               <-- Cache-busting input for forced reinstalls
       ↓
[L2: COPY package.json, configs]     <-- Invalidation point when manifests change (lockfiles are not inputs)
       ↓
[L2: RUN install-deps.sh]            <-- Re-runs to populate node_modules
       ↓
[L3: COPY --link --from=l2 node_modules] <-- Re-runs because source layer changed
       ↓
[L4: Runtime Container]              <-- Rebuilt with updated runtime artifacts
```

1. **Manifest inputs:** As generated by [`l2_dependency_layers.star`](../engine/topologies/platform/docker/layers/l2_dependency_layers.star), the L2 stage copies:
   - `package.json` (workspace root and service directory)
   - `.npmrc` (`.autogenerated/npmrc.docker`)
   - `.bunfig.toml` (`.autogenerated/bunfig.docker.toml`)
2. **Lockfile cache-key behavior:** The L2 generator does **not** copy `bun.lock` or `package-lock.json` into the build context. Consequently, changing *only* a lockfile on the host does **not** invalidate Docker's L2 `COPY` layer cache. To force L2 to re-resolve dependencies when only lockfile or transitive dependencies change without modifying `package.json`, use the `CACHE_BUSTER` argument (`--build-arg CACHE_BUSTER=$(date +%s)`).
3. **Cascading invalidation:** When `package.json` (or `CACHE_BUSTER`) changes, its layer hash changes. This invalidates Docker's cache for the `COPY` step, forcing `install-deps.sh` to re-execute. Next, L3 (`l3_builder_layers.star`) copies `/app/<service>/node_modules` and `/app/node_modules/.bun` from L2 via `COPY --link --from=l2_deps_manifest`. Because L2's files changed, L3 rebuilds, and finally L4 rebuilds.
4. **Why this design is intentional:** When you edit your application source code (e.g. `src/index.ts`), the manifest files and `CACHE_BUSTER` remain untouched. Docker completely skips L1 and L2, reusing the cached `node_modules` layer in under a second.

### Where L2 is generated and configured

- **Service Dockerfile generation:** [`l2_dependency_layers.star`](../engine/topologies/platform/docker/layers/l2_dependency_layers.star) defines `L2_generate_dependency_manifest`, emitting stage `l2_deps_manifest`:
  ```dockerfile
  # ---- L2: dependency_manifest ----
  FROM <project>-l2:latest AS l2_deps_manifest
  WORKDIR /app

  ARG CACHE_BUSTER=2026-06-25-v1
  RUN echo "Cache buster: ${CACHE_BUSTER}"

  COPY package.json ./package.json
  COPY <service>/.autogenerated/npmrc.docker /app/.npmrc
  COPY <service>/.autogenerated/bunfig.docker.toml /app/.bunfig.toml

  WORKDIR /app/<service>
  COPY <service>/package.json ./package.json
  COPY <service>/.autogenerated/npmrc.docker .npmrc
  COPY <service>/.autogenerated/bunfig.docker.toml .bunfig.toml

  COPY shared-platform-engineering/docker-templates/install-deps.sh /usr/local/bin/install-deps.sh
  RUN --mount=type=cache,target=/cache/bun,sharing=shared \
      chmod +x /usr/local/bin/install-deps.sh && \
      /usr/local/bin/install-deps.sh
  RUN mkdir -p /app/node_modules/.bun
  ```
- **Golden base image:** [`golden_image_dockerfile.star`](../engine/topologies/platform/docker/build/golden_image_dockerfile.star) builds the `<project>-l2:latest` golden image with pre-created `/cache/bun` and `/cache/prisma` directories.
- **Install runner:** [`shared-platform-engineering/docker-templates/install-deps.sh`](../shared-platform-engineering/docker-templates/install-deps.sh) runs `bun install --force` with concurrency guards (`BUN_INSTALL_CONCURRENCY=4`), timeout enforcement (`INSTALL_TIMEOUT_SECONDS`), and private Verdaccio registry detection.

## Failures and how to fix them

### 1. The lockfile is missing or out of date, so the frozen install fails

When dependency verification runs in CI or pre-commit checks with frozen lockfile enforcement enabled, the package manager verifies that the lockfile strictly matches `package.json`. If a dependency was modified in `package.json` without updating the lockfile, the frozen install fails.

> **Note on L2 installer vs host/CI checks:** TDK's generated L2 build runner (`install-deps.sh`) executes `bun install --force` and does **not** pass `--frozen-lockfile`. The frozen lockfile failures documented below occur during host-level verification, CI workflows (`.github/workflows/ci.yml`), or custom production Dockerfiles that enforce strict lockfile immutability, rather than during standard `tdk up` image builds.

#### Case 1A: Out-of-date lockfile in Bun (`bun install --frozen-lockfile`)

This is a standalone diagnostic. The generated L2 build runs `install-deps.sh`, which executes `bun install --force` without `--frozen-lockfile`, so this error is not the install command that a `tdk up` image build runs.

**Symptom:**
```text
bun install v1.3.11 (af24e281)
Resolving dependencies
Resolved, downloaded and extracted [16]
error: lockfile had changes, but lockfile is frozen
note: try re-running without --frozen-lockfile and commit the updated lockfile
```
The command terminates with exit code 1.

- **Cause:** `package.json` contains a new, updated, or removed dependency, but `bun.lock` (or `bun.lockb`) was not updated on the host or was not committed to Git.
- **Fix:**
  1. On the host machine, run:
     ```bash
     bun install
     ```
  2. Inspect the changes with `git diff bun.lock` (or `git status`).
  3. Commit both `package.json` and `bun.lock`.
- **Command that confirms it:**
  ```bash
  bun install --frozen-lockfile
  ```
  When valid, it exits 0 without error.

#### Case 1B: Empty or corrupted lockfile in Bun

**Symptom:**
```text
bun install v1.3.11 (af24e281)
error: Missing lockfile version
    at bun.lock:1:1
InvalidLockfileVersion: failed to parse lockfile: 'bun.lock'

warn: Ignoring lockfile
error: lockfile had changes, but lockfile is frozen
```

- **Cause:** An empty file (`touch bun.lock`), a merge conflict marker (`<<<<<<< HEAD`), or a truncated lockfile is present in the project. Because Bun cannot parse the version header, it ignores the file, attempts to generate a new resolution tree, and immediately triggers the `lockfile is frozen` error.
- **Fix:**
  1. Inspect the lockfile header:
     ```bash
     head -n 5 bun.lock
     ```
  2. Regenerate a clean lockfile:
     ```bash
     rm -f bun.lock bun.lockb
     bun install
     ```
  3. Commit the regenerated `bun.lock`.
- **Command that confirms it:**
  ```bash
  bun install --frozen-lockfile
  ```

#### Case 1C: Missing or out-of-sync lockfile in npm workflows (`npm ci`)

This case applies to standalone Node.js projects, CI workflows, or custom services that install with `npm` instead of Bun. `npm ci` gives clean, deterministic installs in those workflows. The standard TDK L2 generator ([`l2_dependency_layers.star`](../engine/topologies/platform/docker/layers/l2_dependency_layers.star)) does not run `npm ci`: it targets Bun and runs `install-deps.sh`, so these errors do not come from a generated L2 build.

**Symptom when `package-lock.json` is missing:**
```text
npm error code EUSAGE
npm error
npm error The `npm ci` command can only install with an existing package-lock.json or
npm error npm-shrinkwrap.json with lockfileVersion >= 1. Run an install with npm@5 or
npm error later to generate a package-lock.json file, then try again.
```

**Symptom when `package-lock.json` is out of sync with `package.json`:**
```text
npm error code EUSAGE
npm error
npm error `npm ci` can only install packages when your package.json and package-lock.json or npm-shrinkwrap.json are in sync. Please update your lock file with `npm install` before continuing.
npm error
npm error Missing: is-even@1.0.0 from lock file
npm error Missing: is-odd@0.1.2 from lock file
```

- **Cause:** A dependency was added or modified in `package.json`, but `package-lock.json` was not generated or updated.
- **Fix:**
  1. On the host, update the lockfile without reinstalling all node_modules:
     ```bash
     npm install --package-lock-only
     ```
  2. Or perform a standard install:
     ```bash
     npm install
     ```
  3. Commit `package-lock.json`.
- **Command that confirms it:**
  ```bash
  npm ci --dry-run
  ```

### 2. A dependency change does not invalidate the cache when it should

#### Symptom:
You updated a dependency (such as publishing a bugfix to a local workspace package, bumping an internal library in Verdaccio, or changing a dependency on disk), but when running `tdk up` or building the container, Docker outputs (shown with `docker build --progress=plain`; step numbers come from one example service and vary):
```text
#17 [l2_deps_manifest  4/13] COPY package.json ./package.json
#17 CACHED
...
#22 [l2_deps_manifest 12/13] RUN --mount=type=cache,target=/cache/bun,sharing=shared chmod +x /usr/local/bin/install-deps.sh && ...
#22 CACHED
```
Docker reuses the cached L2 layer (`CACHED`), and the container continues running with the old dependency code, causing `TypeError: ... is not a function` or missing export runtime errors.

#### Causes:
1. **Manifest files unchanged:** Docker computes cache keys from the checksums of files named in `COPY` instructions. In `L2_generate_dependency_manifest`, the copied files are:
   - `package.json` (workspace root and service directory)
   - `.npmrc` (`.autogenerated/npmrc.docker`)
   - `.bunfig.toml` (`.autogenerated/bunfig.docker.toml`)
   Because `bun.lock` and `package-lock.json` are **not** copied by `L2_generate_dependency_manifest`, modifying only a lockfile on the host or changing an unpinned dependency range (`"lib": "^1.0.0"`) leaves all copied manifest files identical. Docker evaluates `COPY package.json` as a cache hit and skips `install-deps.sh`.
2. **Stale BuildKit cache mount (`/cache/bun`):** The install script mounts `/cache/bun` via `--mount=type=cache,target=/cache/bun,sharing=shared`. If a package was republished to a local registry (like Verdaccio) under the same version tag (mutable version), Bun checks `/cache/bun`, sees the tarball already present, and does not fetch the new bytes.
3. **Lockfile not in the L2 generator's cache key:** Since `l2_dependency_layers.star` does not copy lockfiles, changes to `bun.lock` or `package-lock.json` alone never invalidate the L2 Docker layer cache. Updating dependencies without changing `package.json` requires explicit cache busting via the `CACHE_BUSTER` build argument.

#### Fixes:
- **Option 1: Bust the L2 cache via `CACHE_BUSTER` argument (Required for lockfile-only updates)**
  The L2 Dockerfile includes a cache-busting argument:
  ```dockerfile
  ARG CACHE_BUSTER=2026-06-25-v1
  RUN echo "Cache buster: ${CACHE_BUSTER}"
  ```
  Pass a new value during build to force Docker to re-run from that step onwards. The golden images (`<project>-l1` to `-l4`) must already exist, so run `tdk up` once first:
  ```bash
  docker build --build-arg CACHE_BUSTER=$(date +%s) -f "$SERVICE_PATH/.autogenerated/Dockerfile.app.autogenerated" --target production .
  ```
  Set `SERVICE_PATH` to the affected service directory (for example, `services/api`) before running the command. Run it from the project root, because the L2 stage copies files relative to the build context. This builds the service's generated Dockerfile, which contains the `l2_deps_manifest` stage, rather than the golden-layer Dockerfile.
  With a new `CACHE_BUSTER` value, the `COPY` and install steps run again instead of reporting `CACHED`:
  ```text
  #10 [l2_deps_manifest  3/13] RUN echo "Cache buster: bust2"
  #10 1.420 Cache buster: bust2
  #11 [l2_deps_manifest  4/13] COPY package.json ./package.json
  #11 DONE 0.3s
  ...
  #19 [l2_deps_manifest 12/13] RUN --mount=type=cache,target=/cache/bun,sharing=shared chmod +x /usr/local/bin/install-deps.sh && ...
  #19 DONE 15.5s
  ```
  *(Note: `TDK_GOLDEN_REBUILD=1` only forces golden base image resources past their freshness check. It does not change `CACHE_BUSTER` or invalidate per-service `l2_deps_manifest` layers when manifests are unchanged.)*
- **Option 2: Change the contents of or bump `package.json`**
  Because `package.json` is a direct input to L2's `COPY` instruction, changing its contents or bumping a version in it immediately invalidates Docker's layer cache for that service. A timestamp-only touch does not change the file's contents, so Docker's `COPY` cache still hits.
- **Option 3: Clear BuildKit cache**
  To purge cached packages stored in BuildKit cache mounts (`/cache/bun`):
  ```bash
  docker builder prune -f
  ```

#### Command that confirms it:
Check the installed package version directly inside the built container:
```bash
docker run --rm <image-name> bun pm ls
```
Or for Node services:
```bash
docker run --rm <image-name> npm list --depth=0
```

### 3. The install works on the host but fails inside the image

A dependency installs cleanly on the developer's machine (e.g. macOS Darwin on Apple Silicon or Ubuntu), but fails during the container build stage.

#### Case 3A: Native C++ bindings fail in Alpine Linux (musl libc vs glibc)

**Symptom** (captured with `bun add bcrypt@5.0.1` in the `<project>-l2` golden image, Alpine on arm64):
```text
node-pre-gyp http GET https://github.com/kelektiv/node.bcrypt.js/releases/download/v5.0.1/bcrypt_lib-v5.0.1-napi-v3-linux-arm64-musl.tar.gz
node-pre-gyp ERR! install response status 404 Not Found on https://github.com/kelektiv/node.bcrypt.js/releases/download/v5.0.1/bcrypt_lib-v5.0.1-napi-v3-linux-arm64-musl.tar.gz
node-pre-gyp WARN Pre-built binaries not installable for bcrypt@5.0.1 and node@24.3.0 (node-v137 ABI, musl) (falling back to source compile with node-gyp)
gyp ERR! find Python
gyp ERR! find Python checking if "python3" can be used
gyp ERR! find Python - executable path is ""
gyp ERR! find Python - "" could not be run
...
error: install script from "bcrypt" exited with 1
```
A package that ships a glibc-only prebuilt binary can instead fail at load time with `ERR_DLOPEN_FAILED` / `Exec format error`. That variant was not reproduced for this guide.

- **Cause:**
  1. **musl vs glibc:** The host machine is macOS or a glibc-based Linux distribution. The container runs **Alpine Linux** (`oven/bun:1.3.11-alpine`), which uses **musl libc**.
  2. Prebuilt binaries built for glibc fail to load under musl with `Exec format error` / `ERR_DLOPEN_FAILED`.
  3. When the package falls back to compiling from source via `node-gyp`, compilation fails because `python3`, `make`, and `g++` were deliberately removed from TDK's L2 base image to keep the image lightweight (-67 MB, as noted in `golden_image_dockerfile.star`); the `find Python` lines above show this.
- **Fix:**
  1. Prefer pure JavaScript or TypeScript libraries, or packages that supply official Alpine musl prebuilds (e.g. `@prisma/client`, `esbuild`, `@biomejs/biome`).
  2. If the native package requires glibc compatibility, install `gcompat` in a custom layer:
     ```dockerfile
     RUN apk add --no-cache gcompat
     ```
  3. If compilation is mandatory, install the build toolchain before `install-deps.sh`:
     ```dockerfile
     RUN apk add --no-cache python3 make g++
     ```
     With the toolchain installed, `bun add bcrypt@5.0.1` built from source in the `<project>-l2` image (58 packages installed in 30s) and `require('bcrypt')` loaded.
- **Command that confirms it:**
  Inspect missing shared libraries inside the container:
  ```bash
  docker run --rm <image-name> ldd /app/node_modules/<package>/<binary>.node
  ```
  For a musl build it lists `libc.musl-*` entries. `ldd` does not load Bun's runtime, so it also prints `Error relocating ...: napi_* symbol not found` lines for Node-API addons; those are expected and are not the failure being diagnosed.

#### Case 3B: Private registry (Verdaccio) or credentials unreachable inside container

**Symptom:**
```text
⏱️ install-deps start: 2026-10-14 14:17:43 +0000
🔧 Bun concurrency: 4, Threadpool: 4
🔍 Checking Verdaccio registry at http://localhost:4873...
   localhost unreachable, trying http://host.docker.internal:4873...
❌ Verdaccio not reachable at localhost:4873 or host.docker.internal:4873. Build will fail.
   Ensure Verdaccio is running: docker ps | grep verdaccio
install-deps duration: 1s
```
Or when installing private scoped packages without credentials:
```text
error: GET https://registry.npmjs.org/@myorg%2fprivate-pkg - 404
error: @myorg/private-pkg@1.0.0 failed to resolve
```

- **Cause:**
  1. On the host, the developer is logged into npm via `~/.npmrc`, or has an active VPN/SSH tunnel.
  2. Inside Docker, container builds do not inherit the host's `~/.npmrc` unless explicitly configured.
  3. As seen in [`install-deps.sh`](../shared-platform-engineering/docker-templates/install-deps.sh), when `TDK_LICENSE_KEY` is set, TDK attempts to route private package downloads through Verdaccio at `localhost:4873` or `host.docker.internal:4873`. If the Verdaccio container is stopped, the build terminates immediately.
- **Fix:**
  1. If Verdaccio is required, verify that its container is running:
     ```bash
     docker ps | grep verdaccio
     ```
  2. If Verdaccio is not needed and you are using public npm, ensure `TDK_LICENSE_KEY` is unset:
     ```bash
     unset TDK_LICENSE_KEY
     ```
  3. For private npm tokens, configure the token in `.autogenerated/npmrc.docker` or set `BUN_AUTH_TOKEN` in your environment.
- **Command that confirms it:**
  Test registry connectivity directly from the container's network namespace (matching `install-deps.sh`'s probe):
  ```bash
  docker run --rm oven/bun:1.3.11-alpine sh -c "wget -q --spider --timeout=3 http://host.docker.internal:4873 && echo 'Verdaccio reachable from container'"
  ```

#### Case 3C: Host `node_modules` leaked into container build context

**Symptom:**
The image builds, but when the container starts it fails immediately with:
```text
exec /usr/local/bin/bun: no such file or directory
```
or
```text
Error: Cannot find module '/app/dist/index.js'
```
or native binaries throw:
```text
cannot execute binary file: Exec format error
```

- **Cause:** The project's `.dockerignore` is missing or does not include `node_modules/`. When Docker executes `COPY . .`, the host's Darwin/macOS `node_modules` directory is copied into the container, overwriting the Linux-native packages installed in L2.
- **Fix:**
  1. Verify that `.dockerignore` excludes `node_modules` and build output from entering the Docker build context:
     ```text
     **/node_modules
     **/dist
     ```
     *(Note: `.tiltignore` controls Tilt file-watch events, but only `.dockerignore` prevents files from entering Docker's build context during `COPY` instructions).*
  2. Run `tdk config verify` to verify that generated ignore files match expectations:
     ```bash
     tdk config verify
     ```
  3. If out of sync, run:
     ```bash
     tdk config regenerate
     ```
- **Command that confirms it:**
  ```bash
  tdk config verify
  ```
