# Five terminal clips (#1446)

Each clip shows one command, its real output, and one claim. Every command below was run against the installed CLI (`tdk` 1.3.178) in a scratch project before it was written here. Outputs are copied from those runs. Paths are shortened to `…` where they are local to the machine.

Setup used for clips 1-4 (run in an empty folder):

```bash
tdk project --yes
tdk resource api --type backend --stack shop --yes
tdk resource web --type frontend --stack shop --yes
```

**Caption:** `tdk up shop --dry-run` shows the services and URLs. Nothing starts.

**Claim:** the preview shows what would start before any container does.

Command:

```bash
tdk up shop --dry-run
```

Real output (trimmed to the first lines; the full run also prints the Tilt command line):

🔧 Backend API URLs:
  - api: http://api.shop.localhost:8080/api/api/health
Host ports: HTTP 8080, HTTPS 8443, Postgres 15433
...
Dry run - not starting services

Ports depend on what is free on the machine (the output picks from a fallback range). The clip should say so in the caption, or show the URLs without the port line if the ports differ on the day.

3. Hold on the URLs for 3 s.

## Clip 2: hand-editing a generated file

**Caption:** Edit a generated file by hand and `tdk config verify` says it is out of sync.
**Length:** 40 s.
**Claim:** verify catches hand edits to generated files, and regenerate fixes them.

Commands and real output, in order:

```bash
echo '// hand edit' >> .tdk/.tdk-out/Tiltfile
tdk config verify
```

```text
🔍 Verifying configuration...

ℹ️  Postgres will start because database-management is enabled (generated Tiltfile/spec.master) (project-wide; not a tdk up selection)
⚠️  Configuration issues found:
   - Out of sync: .tdk/.tdk-out/Tiltfile (run 'tdk config regenerate')

--- a/.tdk/.tdk-out/Tiltfile
+++ b/.tdk/.tdk-out/Tiltfile
...
Run `tdk config regenerate` to fix generated files.
```

Verify exits with code 1 in this case. Then:

```bash
tdk config regenerate
tdk config verify
```

The second verify prints `✅ All files are in sync!` and exits 0.

**Change from #1446:** the issue said to edit a generated `Dockerfile`. In this version, `tdk up` builds `.autogenerated/Dockerfile.app.autogenerated`, which only exists after a `tdk up` has run. The scaffolded `services/<stack>/<name>/Dockerfile` is not the one `tdk up` builds, and verify does not check it. So the clip edits the generated Tiltfile instead, which verify does check. If the team wants the Dockerfile in the clip, run `tdk up` once first (needs Docker and Tilt) and confirm verify fails on the generated Dockerfile before recording.

Script:
1. Show the generated file exists (`ls .tdk/.tdk-out`).
2. Append the line, run verify, show the "Out of sync" line.
3. Run `tdk config regenerate`, then verify again.

## Clip 3: moving through the stack in `tdk ui`

**Caption:** `tdk ui`: `j` and `k` move between services, `/` searches.
**Length:** 45 s.
**Claim:** the keyboard controls in the TUI.

Command:

```bash
tdk ui
```

Status of this clip: **not recorded**. The keys were checked in source only: `cli/src/commands/ui.tsx` handles `/` for search (line 692) and `k` and `j` for up and down (lines 779 and 782). The checks were made on `main`, not on the installed 1.3.178 build. `tdk ui` needs a real terminal (Ink raw mode); run without one it exits with `Raw mode is not supported`, which is what happened when it was tried from a script. Record it in a real terminal, and check the three keys on the installed build first. If a key differs, change the caption, not the key.

Script (once confirmed):
1. Open `tdk ui` with the two services in the stack.
2. Press `j`, then `k`, to show the selection move.
3. Press `/`, type `api`, show the filtered list.
4. Quit with the key the TUI shows at the bottom of the screen.

## Clip 4: an agent resource next to the rest of the stack

**Caption:** `tdk resource bot --type agent`, then `tdk up` shows it with the other services.
**Length:** 40 s.
**Claim:** an agent is a resource in the same stack, with its own health URL.

Commands and real output:

```bash
tdk resource bot --type agent -s shop -y
tdk up shop --dry-run
```

The resource step prints the location and next steps (`cd services/shop/bot`, `bun install`, `tdk up shop`). The dry run then lists three services:

```text
Would start 3 services from stack "shop"...
  - api
  - bot
  - web
...
  - bot: http://api.shop.localhost:8080/api/bot/health
```

The generated `services/shop/bot/service.json` has `"type": "agent"`, `"agent": { "runtime": "custom", "durability": "files" }` and `"stack": "shop"`.

**Change from #1446:** the issue said the clip shows "an agent with a database and MCP tools". The command in the issue creates an agent with none of those. `service.json` for the generated agent has no database and no MCP tool entries, and `tdk mcp` is a separate command (an MCP server for coding agents), not a tool the agent gets. Do not show a database or MCP tools in this clip unless a run that adds them is recorded here first (`tdk resource --feature <name>` enables features, for example `prisma`, but that was not run for this clip).

Script:
1. Show `tdk resources` with api and web.
2. Run the agent command. Show the `services/shop/bot` line.
3. Run the dry run. Hold on the three services.

## Clip 5: the same two services, before and after

**Caption:** A Compose file becomes one `service.json` per service. Environment values stay in `.env`.
**Length:** 50 s.
**Claim:** `tdk import` reads a Compose file and writes service files, and it does not copy secret values.

Before (`docker-compose.yml`, a real file used for the run):

```yaml
services:
  api:
    build: ./api
    ports:
      - "4000:4000"
    depends_on:
      - db
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: dev
```

Command for the preview:

```bash
tdk import . --dry-run
```

Real output (trimmed):

```text
Found 2 service(s) and 0 job(s) in …
Read only: docker-compose.yml. Lines below name what was not translated.

  .tdk/project.json  [create TDK project]

  db  (service)
    from:      docker-compose.yml [compose]
    image:     postgres:16
    port:      4000 (assigned)
    proxy:     none, private (no single published port)
    env:       POSTGRES_PASSWORD (names only)
    write:     services/compose-demo/db/service.json  [create]
    note:      environment values are not written; put them in the project .env

  api  (service, api/)
    ...
    health:    / (assumed)
    depends:   db
    note:      health path / is assumed: Compose has no HTTP healthcheck URL. ...

Dry run: nothing written.
```

After (the write step, run in a copy of the folder):

```bash
tdk import . --yes
```

```text
  wrote services/compose-after/db/service.json
  wrote services/compose-after/api/service.json

Wrote 2 service.json file(s) and created .tdk/project.json.

Next:
  - Put the environment values these services need in .env; values in docker-compose.yml were not copied.
  - Run `tdk up` with TDK core 1.3.145 or later. The import did not start anything.
```

Two things the clip must show, both printed by the tool: the health path `/` is an assumption, and `POSTGRES_PASSWORD` moves to `.env` by name only.

Script:
1. Show the Compose file (5 lines).
2. Run `--dry-run`. Hold on the "environment values are not written" line.
3. Run `--yes` in the copy. Show the two `wrote` lines.
