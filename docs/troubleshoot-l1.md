# Troubleshooting: L1 (base image) Docker build failures

This guide covers failures in **L1**, the foundational base image layer of TDK's Docker image stack. It explains what L1 builds, how it relates to the rest of the L1–L4 stack, and how to diagnose and fix the errors you see when L1 fails to build or is missing.

All errors shown on this page were reproduced on a developer workstation running macOS with Docker Desktop.

---

## What L1 is in plain words

TDK uses a four-tier layered Docker architecture (L1–L4) to make local image builds fast and cache-friendly across multiple microservices:

| Layer | Name | Purpose | What it contains | Defined in |
|---|---|---|---|---|
| **L1** | **Base OS & Runtime** | Foundational OS & runtime environment | Alpine Linux base, Bun runtime (`oven/bun:1.3.11-alpine`), essential utilities (`curl`, `bash`, `openssl`, `ca-certificates`, `tzdata`), `app` system user/group, and runtime env vars (`NODE_ENV`, `BUN_INSTALL_CACHE_DIR`). | [`l1_base_layers.star`](../engine/topologies/platform/docker/layers/l1_base_layers.star) |
| **L2** | Dependencies | Package resolver & module cache | Base layer + common dependencies + pre-warmed `/cache/bun` directory. | [`l2_dependency_layers.star`](../engine/topologies/platform/docker/layers/l2_dependency_layers.star) |
| **L3** | Builder | Compilation & asset building | Service compilation, Prisma CLI, frontend bundler, and production pruning. | [`l3_builder_layers.star`](../engine/topologies/platform/docker/layers/l3_builder_layers.star) |
| **L4** | Runtime | Final production/dev container | Lean runtime (Bun for backends, Nginx or Bun static for frontends, migrator). | [`l4_runtime_layers.star`](../engine/topologies/platform/docker/layers/l4_runtime_layers.star) |

L1 is the root of the entire stack. Every generated service Dockerfile (`.autogenerated/Dockerfile.*.autogenerated`) and all subsequent golden layers (L2, L3, L4) inherit from L1. If L1 fails to build or is missing from local Docker storage, downstream builds cannot start.

### Where L1 is generated and built

1. **Dockerfile definition:** The L1 stage is emitted into `.tdk/.tdk-out/golden-layers.Dockerfile` by [`golden_image_dockerfile.star`](../engine/topologies/platform/docker/build/golden_image_dockerfile.star):
   ```dockerfile
   # L1: OS BASE + RUNTIME ENVIRONMENT
   FROM oven/bun:1.3.11-alpine@sha256:7ed9f74c326d1c260abe247ac423ccbf5ac92af62bb442d515d1f92f21e8ea9b AS l1_golden

   LABEL layer="l1" \
         description="OS base with runtime environment" \
         maintainer="<project>"

   RUN apk add --no-cache \
       ca-certificates \
       tzdata \
       curl \
       bash \
       openssl

   RUN addgroup -S app && adduser -S app -G app

   ENV NODE_ENV=development \
       BUN_INSTALL_CACHE_DIR=/cache/bun

   WORKDIR /app
   ```
2. **Build orchestration:** The Tilt resource `golden-layers-build` (in [`golden_image_build.star`](../engine/topologies/platform/docker/build/golden_image_build.star)) builds target `l1_golden` and tags it locally as `<project>-l1:latest` (or `tdk-project-l1:latest`).

## Failures and how to fix them

### 1. The base image cannot be pulled

When L1 begins building, Docker must resolve and pull the upstream base image:
`oven/bun:1.3.11-alpine@sha256:7ed9f74c326d1c260abe247ac423ccbf5ac92af62bb442d515d1f92f21e8ea9b`.

#### Case 1A: Docker daemon is not running

**Symptom:**
```text
$ docker build -f .tdk/.tdk-out/golden-layers.Dockerfile --target l1_golden -t <project>-l1:latest .
ERROR: Cannot connect to the Docker daemon at unix:///Users/<user>/.docker/run/docker.sock. Is the docker daemon running?
```

**What `tdk doctor` prints:**
```text
$ tdk doctor
failed to connect to the docker API at unix:///Users/<user>/.docker/run/docker.sock: connect: no such file or directory
✗ Docker Desktop is open, but its engine is not responding
ℹ Fix: Quit Docker Desktop completely (whale icon > Quit Docker Desktop), reopen it, and wait until it shows Running. If it keeps getting stuck, check free disk space. Then retry: tdk doctor
```
Or when running `tdk up`:
```text
$ tdk up
Cold start blocked. Bun/Prisma/NATS are not the first failure.
They are generated after `tdk project`. Fix the machine checks below.
FAIL docker  Docker daemon is not running
  Start Docker Desktop, OrbStack, or Colima, then retry: tdk doctor
```

- **Cause:** The Docker daemon is stopped, frozen, or starting up.
- **Fix:** Launch Docker Desktop, OrbStack, or Colima. Wait until the whale icon or CLI status reports running (`docker info`), then re-run `tdk doctor` or `tdk up`.

#### Case 1B: Offline or network DNS lookup failure

**Symptom:**
```text
 => ERROR [internal] load metadata for docker.io/oven/bun:1.3.11-alpine
------
 > [internal] load metadata for docker.io/oven/bun:1.3.11-alpine:
------
ERROR: failed to build: failed to solve: oven/bun:1.3.11-alpine: failed to resolve source metadata for docker.io/oven/bun:1.3.11-alpine: failed to do request: Head "https://registry-1.docker.io/v2/oven/bun/manifests/1.3.11-alpine": dial tcp: lookup registry-1.docker.io: no such host
```

- **Cause:** The machine cannot resolve Docker Hub or reach external networks (e.g. offline, captive portal, broken VPN, or corporate firewall blocking `registry-1.docker.io`).
- **Fix:**
  1. Test network connectivity: `curl -I https://registry-1.docker.io/v2/`.
  2. If on a corporate network or proxy, configure the HTTP/HTTPS proxy in **Docker Desktop Settings → Proxies**.
  3. Once connected, retry `tdk up`. To test the pull on its own, use the exact digest-pinned reference the build uses (a bare tag can resolve to a different image):
     ```bash
     docker pull oven/bun:1.3.11-alpine@sha256:7ed9f74c326d1c260abe247ac423ccbf5ac92af62bb442d515d1f92f21e8ea9b
     ```

#### Case 1C: Registry rate limit (Docker Hub 429 Too Many Requests)

**Symptom:**
```text
ERROR: failed to build: failed to solve: toomanyrequests: You have reached your unauthenticated pull rate limit. Please see https://docs.docker.com/docker-hub/download-rate-limit/
```

- **Cause:** Docker Hub enforces a limit of 100 anonymous pulls per 6 hours per IP address. Shared office networks and CI runners frequently hit this limit.
- **Fix:**
  1. Authenticate with Docker Hub using `docker login`:
     ```bash
     docker login -u <username>
     ```
  2. If using a local mirror or pull-through cache, configure `"registry-mirrors"` in Docker daemon settings (`daemon.json`).

### 2. The Alpine package step fails (`apk add`)

During the L1 stage, the Dockerfile executes:
```dockerfile
RUN apk add --no-cache \
    ca-certificates \
    tzdata \
    curl \
    bash \
    openssl
```

#### Case 2A: Alpine package repository DNS / network error

**Symptom:**
```text
 => ERROR [2/4] RUN apk add --no-cache ca-certificates tzdata curl bash openssl
------
 > [2/4] RUN apk add --no-cache ca-certificates tzdata curl bash openssl:
0.108 fetch https://dl-cdn.alpinelinux.org/alpine/v3.22/main/aarch64/APKINDEX.tar.gz
2.467 WARNING: fetching https://dl-cdn.alpinelinux.org/alpine/v3.22/main: DNS lookup error
2.467 ERROR: unable to select packages:
2.467   curl (no such package):
2.467     required by: world[curl]
------
ERROR: failed to build: failed to solve: process "/bin/sh -c apk add --no-cache ca-certificates tzdata curl bash openssl" did not complete successfully: exit code: 1
```

- **Cause:** (The pinned `oven/bun` image is Alpine 3.22.3, checked with `cat /etc/alpine-release`, so the `v3.22` URLs above are the ones the build uses.) The build container cannot resolve or reach `dl-cdn.alpinelinux.org`. Docker container DNS is separate from host DNS; if your host network changes (e.g. switching Wi-Fi, toggling a VPN), the Docker daemon's internal DNS resolver may fail.
- **Fix:**
  1. Find out where the failure is. From the host: `curl -I https://dl-cdn.alpinelinux.org/alpine/`. From inside a container (any image with `ping`, used here only as a DNS test, not the L1 base):
     ```bash
     docker run --rm alpine ping -c 2 dl-cdn.alpinelinux.org
     ```
     If the host works and the container does not, the problem is Docker's DNS or egress, not Alpine.
  2. Restart Docker Desktop (or toggle the VPN back) and retry `tdk up`. This is enough after a network change.
  3. Only if that fails, and only where your network allows public resolvers, set DNS in **Settings → Docker Engine**: `{"dns": ["8.8.8.8", "1.1.1.1"]}`. On corporate networks or VPNs with internal DNS these may be blocked or break private names; remove the `dns` key to restore the default.

### 3. Golden image is missing (Pull access denied for `<project>-l1:latest`)

TDK's golden images (`<project>-l1:latest`, `<project>-l2:latest`, `<project>-l3-backend:latest`, `<project>-l4-backend:latest`) are **local-only images** built on your machine. They are never pushed to or pulled from Docker Hub.

#### Symptom:
When starting services or building an individual service before the golden layers finish building, Docker attempts to pull the image from Docker Hub and fails:

```text
 => ERROR [internal] load metadata for docker.io/library/tdk-project-l1:latest
------
 > [internal] load metadata for docker.io/library/tdk-project-l1:latest:
------
ERROR: failed to build: failed to solve: tdk-project-l1:latest: failed to resolve source metadata for docker.io/library/tdk-project-l1:latest: pull access denied, repository does not exist or may require authorization: server message: insufficient_scope: authorization failed
```

In the Tilt web UI, the service resource turns red with:
```text
pull access denied for docker.io/library/<project>-l1:latest
```

#### Cause:
1. **Race condition during first startup:** Tilt started compiling/building a service container before the `golden-layers-build` local resource finished producing the golden images.
2. **Pruned Docker images:** A cleanup command such as `docker system prune -a` or `docker rmi` removed the locally built `<project>-l*` images.
3. **Mismatched project prefix:** If `.tdk/project.json` has a different `"name"`, service Dockerfiles reference `<project>-l1:latest` while existing local images may carry another prefix.

#### How to verify if the L1 golden image exists:
Run:
```bash
docker image ls "*l1*"
```
If the image exists, you will see output like:
```text
REPOSITORY              TAG       IMAGE ID       CREATED          SIZE
tdk-project-l1          latest    ae5f25bdb9bc   10 minutes ago   180MB
```
If nothing is returned, the L1 golden image has not been built or was deleted.

#### How to rebuild the L1 golden image:

- **Method 1: Force rebuild via TDK (Recommended)**
  Set `TDK_GOLDEN_REBUILD=1` and run `tdk up`:
  ```bash
  TDK_GOLDEN_REBUILD=1 tdk up
  ```
  This tells the `golden-layers-build` Tilt resource to ignore cache hashes and rebuild all golden layers.

- **Method 2: Trigger in Tilt**
  If Tilt is already running, open the Tilt web UI (`http://localhost:10350` or the port printed by `tdk up`), find the **`golden-layers-build`** resource, and click the manual reload/trigger button. Once it turns green, trigger the failed service resources.

- **Method 3: Build the L1 target directly with Docker (diagnostic only)**
  This isolates whether the Dockerfile itself builds. It does not run TDK's orchestration, so it is not a full recovery: the later golden layers are not rebuilt and the hash TDK checks is not refreshed.
  ```bash
  docker build -f .tdk/.tdk-out/golden-layers.Dockerfile --target l1_golden -t <project>-l1:latest .
  docker image ls "*l1*"
  ```
  Confirm the tag matches what the service Dockerfiles use, then run Method 1 or 2 so `golden-layers-build` rebuilds L2–L4 on top of it.
