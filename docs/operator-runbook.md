# Operator runbook

One page for whoever installs, supports, or releases the TDK CLI. Details live in the linked pages.

## Install and support matrix

| Host | `tdk up` | Other commands |
| --- | --- | --- |
| macOS | supported | supported |
| Linux | supported | supported |
| WSL2 Ubuntu | supported (see [wsl2.md](wsl2.md)) | supported |
| Native Windows | not supported; refuses with "Native Windows is inspect-only" | inspect-only |

`tdk up` needs Docker and Tilt on the host. Run `tdk doctor` to check them.

## Versions `tdk doctor` checks

`tdk doctor` enforces minimums, not exact pins:

| Tool | Minimum |
| --- | --- |

## Generated files and drift

For a file-by-file guide to service outputs, see [Generated service files](generated-files.md).

`tdk up` checks generated service files (under `.autogenerated/`) against their snapshot before Tilt starts. Editing `service.json` and running `tdk up` is the normal loop and is not drift: `tdk up` regenerates the outputs.

- If a generated service file was edited by hand, `tdk up` exits 2 and lists it. Restore the saved content or move the intended change into `service.json`; the CLI also suggests `tdk config regenerate`, which rewrites project files rather than the service output itself.
- `tdk config verify` runs a wider check: it compares generated project files, validates discovered service manifests, and checks generated service snapshots. It prints diffs for project files and names service errors.
- `tdk up --dry-run` runs the same check and exits 2 on drift, so you can see it without starting anything.
- `tdk up --ignore-drift` skips the check and always prints a warning, whether or not anything drifted, because the check did not run.
- A missing `.tdk-contract` snapshot is reported by `tdk config verify` as an error, but it does not block `tdk up`: only files that differ from an existing snapshot count as hand edits. A project with no `.tdk/project.json` is not checked.

## Importing an existing repo

`tdk import` runs the published importer, [`@tdk-landscape/tdk-import`](https://www.npmjs.com/package/@tdk-landscape/tdk-import), at the exact version pinned in `cli/src/commands/import.ts` (`IMPORT_PACKAGE`). `TDK_IMPORT_PACKAGE` overrides it. When a new importer is published, move the pin in a CLI release.

It reads one file, the root `docker-compose.yml`, and writes one bring-your-own `service.json` per Compose service, plus `.tdk/project.json` if the directory is not a TDK project. It does not read other Compose file names, override files, Dockerfiles, `package.json` or Procfiles, and it names what it did not translate. See the importer's [import.md](https://github.com/tdk-landscape/tdk-import/blob/main/docs/import.md) for the mapping.

```bash
tdk import <dir> --dry-run
tdk import <dir> --yes
```

Start the imported stack with TDK core **1.3.145 or later**. 1.3.104 added `buildContext` ([tdk-cli-core#525](https://github.com/tdk-landscape/tdk-cli-core/pull/525)); 1.3.145 generates the Tiltfile for a project that has `.tdk/project.json` but none yet ([tdk-cli-core#1018](https://github.com/tdk-landscape/tdk-cli-core/pull/1018)). `tdk import` enforces that the installed core is at least 1.3.104 before writing; if an older core is encountered, it exits before writing and prints the upgrade command (`tdk upgrade`).

Put the environment values the services need in the project `.env`; values in the Compose file are never copied. Evidence of the importer running through a real `tdk up`: [#1007](https://github.com/tdk-landscape/tdk-cli-core/issues/1007).

## Cutting a release

The normal release is the workflow, from a release branch (see the publish gate in [#1631](https://github.com/tdk-landscape/tdk-cli-core/pull/1631)):

1. Cut `release/rc-<timestamp>` at the commit to ship, and run the Release candidate workflow on it. Wait for it to pass.
2. Run `gh workflow run release-binaries.yml --ref release/rc-<timestamp>`. The workflow picks the next unpublished version, builds and checks the binaries, publishes the npm package and the release in `tdk-landscape/tdk-cli-releases`, and credits fixed issues.
3. The workflow does not commit the version it published. Open a PR on `main` that sets `version` in `package.json` and `cli/package.json` to that version, so `main` matches npm.
4. The installer verifies each binary against `checksums.txt`.

To build a binary by hand, without publishing, run `scripts/release-binaries.sh`. It writes `tdk-linux-{amd64,arm64}`, `tdk-darwin-{amd64,arm64}`, `tdk-windows-amd64.exe`, `tdk-cli-engine.tar.gz`, and `checksums.txt` (SHA-256) into `release-dist-<version>/`. `scripts/release-binaries.sh --publish` creates a draft release, downloads every asset, compares bytes with the local build, and only then publishes it as latest. `--publish-only` reuses an existing `release-dist-<version>/`.

### Publish gate

`release-binaries.yml` publishes to npm only when a passing **Release candidate** run (`release-candidate.yml`) covers the commit being released. Dispatch the release on `main`, and the `publish` job checks this first with `scripts/check-release-candidate.mjs`:

- **Exact commit:** a passing candidate ran on the same commit. This is the normal case.
- **Ancestor commit:** a passing candidate ran on an earlier commit, and no commit since changed a release input. The release inputs are the paths the `changes` job filters on (`cli/**`, `engine/**`, `package.json`, `bun.lock`, `Tiltfile`, `discovery/**`, `specs/**`, `ext/**`, `scripts/release-binaries.sh`, `shared-platform-engineering/docker-templates/**`, and `release-binaries.yml` itself). CI-only and docs-only commits do not invalidate a candidate.
- **Otherwise** the gate fails and lists, for each candidate, why it does not cover the commit (for example `release inputs changed since (cli/**)`). Run a new candidate on the commit, then re-run publish.

To start a candidate on the commit you want to release, push an `rc-*` tag at it or run the Release candidate workflow on a `release/*` branch. Candidates are not run on every push, so a dispatch on `main` will fail until one covers the commit. Check the commit with the gate before you dispatch:

```bash
GH_TOKEN="$(gh auth token)" node scripts/check-release-candidate.mjs --sha <commit> --repo tdk-landscape/tdk-cli-core
```

Tracked in [#1627](https://github.com/tdk-landscape/tdk-cli-core/issues/1627).

## License key

`TDK_LICENSE_KEY` is optional. `tdk up` still runs the free stack when the key is unset, invalid, or expired. The cases differ in what `tdk up` does:

| Key state | Premium-bundle request | Premium overlay |
| --- | --- | --- |
| Unset | none | none; Verdaccio and Sablier fall back to disabled public stubs and print a message that they need a license |
| Invalid or expired | made, unless a cached result is still fresh | none for a rejected key; an overlay already in `.tdk/.tdk-out/tdk-cli-ext` stays in use |

- Bundle downloads and entitlement checks (grant or denial) are cached per key under `~/.tdk/cache` and reused for up to 12 hours. For that window a key that was just revoked or has just expired can still be treated as entitled, and a key that was denied is not re-checked until the cache expires. Operators will hit this most often.
- `tdk up` does not revalidate the key or re-vendor `.tdk/.tdk-out/tdk-cli-ext`. A premium overlay created while the key was valid can stay in use after the key expires.
- DDD is public code gated separately by `tdk resource --ddd`; it is not a stub.
