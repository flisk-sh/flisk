# Pilot scorecard

At the end of a pilot a lead has to say adopt, extend or stop. This page gives every team the same measurements and the same questions, so results can be compared and shared. Pair it with the [adoption guide](adopt-tdk.md).

## Record a run

From a TDK project, with Docker and `tdk` available:

```bash
scripts/pilot-scorecard.sh -p . -s shop -c warm
```

| Flag | Meaning |
| --- | --- |
| `-p` | Project root containing `.tdk/project.json` (default `.`) |
| `-s` | Stack to start with `tdk up <stack>`; leave out for a plain `tdk up` |
| `-c` | `cold` or `warm`: the image cache state **you** set up before the run. The script never deletes images, and does not verify what you say |
| `-t`, `-i` | Seconds to wait for a healthy stack (default 900), and between the two memory samples (default 30) |

It writes `pilot-scorecard-results/<timestamp>.md` in the project and stops the stack at the end. It records:

- the machine, CPU count, and TDK, Docker and Tilt versions
- seconds until `tdk up` prints `TDK is up.`, and until every service health URL that `tdk up` printed answers HTTP 200
- how many containers the run started, and their combined memory and CPU, at ready and again after the idle wait. Only containers that were **not** running before the run are counted, so other projects on the machine do not inflate it
- which of its containers `tdk down` left running, which the script then removes
- if `tdk doctor` blocks the run, or `tdk up` fails or times out, the log is written to the record instead

## Example record

One scaffolded `backend` service (`tdk resource orders-api --type backend --stack shop`) in an empty directory on a MacBook (arm64, 8 CPUs, TDK 1.3.86, Docker 29.8.0, Tilt 0.37.7), warm image cache, two runs: 23 s and 25 s until the health URL answered 200 (1 service), 3 containers, 49 to 57 MiB combined, 0.4 to 0.8% CPU idle. This is a scaffold, not an application workload and not an adopter, so do not compare your own numbers to it as a benchmark. The first run of the same stack on a cold cache took about 95 s to the first 200, timed by hand, not by the script.

```text
- Tilt started (`TDK is up.`): 1s
- Every service health URL answered 200 (1 checked): 25s
- Containers started by this run: 3
- Memory of those containers: 49.5 MiB at ready, 47.8 MiB after 20s idle
- CPU of those containers (sum of docker stats %): 0.8% at ready, 0.4% after 20s idle
```

## Things seen while building this

- `TDK is up.` appears about a second in, when Tilt starts, not when services are ready. Time to the first 200 on a health URL is the number that means something.
- `tdk doctor` passes while no service is running yet (it skips the ping), so a passing doctor is not a readiness signal either.
- With TDK 1.3.86, the generated service container (`shop-autogenerated-orders-api-1`) and the `tilt up` process were still running after `tdk down`. Cause: `tdk down` ran `tilt down` without `--focus`, so the Tiltfile did not register the stack's compose project. Changed on `main` since 1.3.86 ([#585](https://github.com/tdk-landscape/tdk-cli-core/pull/585), see the changelog): `tdk down` now passes every stack to the Tiltfile and stops this project's `tilt up`, so the script's "After `tdk down`" listing should be empty on a newer TDK. This was not re-measured on a real stack.
- Each project leaves its Docker networks behind after `tdk down` (they are shared and created outside Tilt, so this is deliberate). After several runs plus other projects on the same machine, `tdk doctor` failed with `Docker cannot create another network: all predefined address pools are in use`. `tdk down --prune-networks` removes this project's networks that no container is attached to; `docker network prune` clears every unused network on the machine.

If another project already holds the default ports, `tdk doctor` fails and the record says which container owns them. Set `TDK_HTTP_PORT`, `TDK_HTTPS_PORT` or `TDK_POSTGRES_PORT` for the run and note it.

Run it cold once (remove the images you are about to test first) and warm once, and say which is which. A cold run is dominated by image builds and downloads.

## Fill in by hand

The script leaves these blank; they are the ones a person has to count.

| Metric | How to count it |
| --- | --- |
| Setup steps removed | Steps in your current "get started" page that a new teammate no longer does. Count from the page, not from memory |
| Setup steps added | Commands or concepts TDK made the newcomer learn |
| Onboarding questions | Questions a new teammate asked in chat during their first setup, with and without TDK if you have both |
| CI reliability | Runs of `tdk config verify` and any `tdk up` job, and how many failed for reasons unrelated to the change |
| Decision | Adopt, extend the pilot, or stop, and the main reason in one sentence |

Only quote numbers you measured, with their conditions. Do not present the [claims registry](claims.md) figures as your own results, and do not write that TDK saves weeks of setup: onboarding time has not been measured on a hiring cohort.

## What to check before you start

These are documented limits that most often decide fit. A "yes" to any is a reason to read the linked page before piloting, not a verdict.

- Your Compose file has two or three services and works: [Compose is a better fit](compare-honest.md#compose).
- Developers are on native Windows: startup needs Ubuntu on WSL2 ([WSL2 guide](wsl2.md)).
- Services are not TypeScript, Python, Go or Rust: they run as [bring-your-own resources](byo.md) with no generated code or live update.
- Developers sit behind a TLS-intercepting proxy or use a private registry: [not tested](faq-teams.md#corporate-proxy-vpn-private-registry-custom-ca).
- You want several projects running at once: [running more than two at once is not documented or tested](faq-teams.md#ports-and-running-two-stacks-at-once).
- Machines have little RAM: sizing is [not measured](faq-teams.md#ram-and-cpu-on-a-16-gb-machine) except by this scorecard on your own stack.

## Sharing results

- Memory, CPU and timings can go in a [benchmark issue](https://github.com/tdk-landscape/tdk-cli-core/issues/125) as they are. Remove the project name if it is private.
- To be listed as an adopter, follow [ADOPTERS.md](../ADOPTERS.md): a public repository or write-up, and the TDK version you run. A pilot that you ended does not count, and neither does "evaluating".
- A pilot that stopped is useful too. Open an [issue](https://github.com/tdk-landscape/tdk-cli-core/issues/new/choose) with the decision line and the `tdk doctor` output; you do not have to name the company.
