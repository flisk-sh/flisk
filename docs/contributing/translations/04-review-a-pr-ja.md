# 4. pull request をレビューする

> このページは [04-review-a-pr.md](../04-review-a-pr.md) の翻訳です。内容が異なる場合は英語版が優先されます。

誰でも pull request をレビューできます。すべてのレビューは同じルールに従います。

1. 最初の確認には AI レビューボタンを使う。
2. AI が挙げたすべての点を、自分で差分と照らし合わせて確認する。
3. GitHub で自分のレビューを送信し、確認した内容を書く。

送信するレビューの責任は、AI ではなくあなたにあります。

## 最初のレビューの前に: 必読ドキュメント

レビューの前に以下を読んでください。合計で約 1 時間かかり、一度だけ行えば十分です。これを読まないと、AI のコメントが正しいかどうか判断できません。

**TDK とは**

- [ ] [README](../../../README.md): TDK が何をするか、人々がどのコマンドを使うか。
- [ ] [プロジェクトの概要](../../project-overview.md): Project → Stack → Resource のモデル。
- [ ] [スコープ](../../scope.md): TDK が何のためのもので、何のためのものではないか。
- [ ] [生成されるファイル](../../generated-files.md): TDK が書き出すファイル。生成されたファイルを手で編集してはいけません。それを生み出す入力を変更してください。

**私たちの進め方**

- [ ] [コントリビューションのガイド](../../../CONTRIBUTING.md): ラベル、issue の担当、DCO の sign-off。
- [ ] [1. 変更の準備](01-first-change-ja.md): いつ OpenSpec の提案が必要か。
- [ ] [2. 変更の種類ごとのレシピ](02-feature-recipes-ja.md): コードがどこにあり、各変更にどのチェックが必要か。
- [ ] [3. pull request を作成する](03-open-a-pr-ja.md): 良い PR に何が必要か。変更前後の証拠を含む。

**全員が守るルール**

- [ ] [行動規範](../../../CODE_OF_CONDUCT.md): レビューで互いにどう話すか。
- [ ] [セキュリティポリシー](../../../SECURITY.md): セキュリティの問題は非公開で報告し、PR のコメントでは決して報告しない。
- [ ] [ガバナンス](../../../GOVERNANCE.md)と[メンテナー](../../../MAINTAINERS.md): 誰が決めるか、誰がマージするか。

そのあと一度試してください。[クイックセットアップ](../../../CONTRIBUTING.md#quick-setup)を実行すると、PR をチェックアウトして、そのチェックを自分で実行できます。

## 要点

1. GitHub で PR を開き、説明の末尾までスクロールする。
2. **Review this PR in** の下にある **Grok**、**Claude**、**Codex** のいずれかをクリックする。
3. AI の回答を読む。各点を差分と照らし合わせて自分で確認する。
4. PR で **Files changed** をクリックし、次に **Review changes**（右上。レイアウトによっては **Submit review**）をクリックする。
5. コメントを書き、**Comment**、**Approve**、**Request changes** のいずれかを選んで、**Submit review** をクリックする。

## AI はレビュアーではなく、あなたのアシスタント

AI ボタンは AI アシスタントとのチャットを開きます。そのアシスタントはあなたのものです。あなたのアカウントであなたに答えるもので、チャットは PR の作成者や他のレビュアーと共有されません。GitHub に何かを投稿したり、承認したり、コードを変更したりすることはありません。

レビュアーはあなたです。あなたの名前で GitHub に送信したレビューが、意味を持ちます。そのため、次の点に注意してください。

- **コピーする前に確認する。** AI は間違えることがあります。差分にない問題をでっち上げたり、本物の問題を見落としたりすることがあります。AI が挙げたファイルと行を開き、自分で確認してください。
- **自分の言葉で書く。** 確認して同意した点だけを貼り付けてください。残りは削除してください。
- **確認していないことを書く。** 「コードは読んだが実行はしていない」は、役に立つレビューです。
- **チャットにシークレットを貼らない。** トークン、パスワード、非公開の URL は、AI のチャットにも PR のコメントにも入れてはいけません。

## AI レビューボタンの仕組み

PR が開かれたり、再オープンされたり、編集されたりすると、[AI レビューボタンのワークフロー](../../../.github/workflows/ai-review-buttons.yml)が PR の説明の末尾にこのセクションを追加します。

> **Review this PR in**
> \[Grok\] \[Claude\] \[Codex\]

各ボタンは単なるリンクです。AI のウェブサイトを新しいタブで開き、このメッセージがすでに入力された状態にします。

```text
Review this pull request. Read the title and diff at https://github.com/flisk-sh/tdk-cli-core/pull/123.
```

| ボタン | 開くサイト |
|---|---|
| **Grok** | grok.com |
| **Claude** | claude.ai |
| **Codex** | chatgpt.com |

普段使っているものを選んでください。どれも同じメッセージを受け取ります。各サイトでサインインを求められることがあります。その後でチャットが空の状態で開いたら、もう一度ボタンをクリックしてください。サインインしていない場合は、上のメッセージをコピーし、PR のリンクを入れて、任意の AI チャットに貼り付けてください。

知っておくべきこと:

- **CI では何も実行されません。** ワークフローはリンクを説明文に書き込むだけです。クリックするまで AI は呼び出されません。
- **あなたの文章は安全です。** このセクションは作成者の文章の後に追加され、その文章は変更されません。作成者が同時に説明文を編集している場合、ワークフローは上書きせず更新をスキップします。
- **ボタンが表示されない？** PR の説明を編集して保存してください（小さな変更で構いません）。するとワークフローがボタンを追加します。メンテナーは **Actions** タブからワークフローを手動で実行して、開いているすべての PR にボタンを追加することもできます。

### より良いフォローアップ質問をする

最初の回答は要約です。より役に立つレビューのために、次のような追加の質問をしてください。

- 「既存のユーザーに影響しうる変更はどれですか？ ファイルと行を示してください。」
- 「この差分でテストが欠けている箇所はありますか？」
- 「PR の説明は、コードが実際に行っていることと一致していますか？」
- 「`cli/src/commands/up.ts` の 40〜60 行を、プロジェクトに初めて来た人向けに説明してください。」
- 「確信のある問題について、短くて親しみやすいレビューコメントを書いてください。」

### マージ競合のボタン

PR が `main` と競合する場合、[AI 競合ボタンのワークフロー](../../../.github/workflows/ai-conflict-buttons.yml)が、Grok、Claude、Codex 用の **Resolve conflict** ボタンを付けたコメントを PR に一つ投稿します。これらのボタンは、AI に `main` をブランチにマージして修正を push するための手順を与えます。AI がそのブランチに push できない場合（たとえば自分の所有でないフォーク）、手順は代わりに `fix/<PR number>-conflict` ブランチへ push して、置き換えの PR を開するよう指示します。元の PR に `Fixes #N` と書かれていれば、置き換えの PR にも同じことが書かれます。結果は通常の変更と同じように確認し、元の PR に置き換えの PR へのリンクをコメントしてください。競合が解消されると、同じコメントが解消されたことを示す内容に変わり、ボタンは消えます。

## 何を確認するか

すべてを確認する必要はありません。できる範囲を選び、確認した範囲を書いてください。

- [ ] **説明どおりに動くか？** タイトルと「What changed」を差分と比べる。
- [ ] **一つの焦点を絞った変更か？** 無関係な編集は別の PR にするべきです。
- [ ] **証拠はあるか？** 修正や動作の変更では、PR に実際の変更前後の出力があるべきです（[変更内容を示す](03-open-a-pr-ja.md#変更内容を示す)を参照）。
- [ ] **チェックは通っているか？** **Conversation** タブの下部のチェックを見る。失敗しているチェックは、修正か説明が必要です。
- [ ] **ドキュメントは更新されているか？** 新しいオプションや変更されたコマンドは、そのドキュメントも変更が必要です。
- [ ] **リスクはないか？** シークレット、削除されたファイル、変更されたデフォルト値、新しい依存関係は、質問する価値があります。
- [ ] **理解できるか？** 新参者として、コードを追えない場合はそう書いてください。それも有用なフィードバックです。

## 行にコメントする

1. **Files changed** タブを開く。
2. 行にカーソルを合わせ、現れる青い **+** をクリックする。ドラッグすると複数行を選べます。
3. コメントを入力する。
4. **Start a review**（すでに始めている場合は **Add review comment**）をクリックする。これでコメントは送信するまで下書きとして保存され、作成者は多数ではなく一度だけ通知を受け取ります。

**Add single comment** はすぐに投稿されます。短い質問のときに使い、完全なレビューには使わないでください。

正確な修正案を示すには、コメント欄の **±** アイコン（**Insert a suggestion**）をクリックして、ブロック内のコードを編集します。作成者はワンクリックで適用できます。

## レビューを送信する

**Files changed** の右上にある **Review changes** をクリックし、要約を書いて、3つの選択肢のいずれかを選びます。

### Comment: 判断を伴わないフィードバック

質問や小さなメモがあるとき、または PR の一部だけを確認したときに **Comment** を使ってください。

```markdown
Read the CLI changes; did not run them.

Question: what happens when `--port` is 0? The help text does not say.
```

### Approve: 「準備完了です」、ただしメモ付き

PR を確認して、マージしてよいと判断したときに **Approve** を使ってください。承認しても小さなコメントを残せます。その場合は、作成者がマージを妨げないと分かるように、任意であることを明記してください。

```markdown
Looks good. I ran `bun run test` on this branch and tried `tdk up --dry-run` in the restaurant example: the new URLs show up as described.

Optional (nit): `parsePort` could use a test for an empty string. Fine to do in a follow-up.
```

### Request changes: 「まだです」、理由付き

マージ前に修正が必要なときに **Request changes** を使ってください。これは GitHub 上で PR を却下する方法です。PR は閉じられず、作成者に何を直すべきかが伝わります。何が問題で、どこにあり、何があればよいのかを必ず書いてください。

```markdown
Thanks for this! Two things need fixing before merge:

1. `cli/src/commands/up.ts` line 52: the new flag is read but never passed to the generator, so `--no-cache` has no effect. Could you pass it through and add a test?
2. The README still shows the old flag name `--nocache`.

Everything else looks good. Happy to re-review once these are in.
```

作成者が修正を push したら、**Files changed** をもう一度開き、新しいコミットを確認して、新しいレビューを送信してください。問題が解消されていれば **Approve** を選びます。以前の「変更依頼」は、新しいレビューを送信するまで PR に残ります。

### PR を閉じる

変更を依頼することは、閉じることとは違います。PR を閉じるのはメンテナーだけで、通常は変更が受け入れられない場合や、作成者が応答しなくなった場合です。PR を閉じるべきだと思ったら、**Comment** で理由を書き、判断はメンテナーに任せてください。

## 親切で明確なコメントを書く

- 悪い点だけでなく、良い点も書く。
- 具体的に書く: ファイルと行の名前を挙げ、その理由を説明する。
- 命令ではなく質問をする: 「Change this.」より「Could this be…?」のほうが効果的です。
- 小さな点には `nit:` または `optional:` と付けて、作成者がマージを妨げないと分かるようにする。
- 人ではなくコードをレビューする。

すべてのコメントで[行動規範](../../../CODE_OF_CONDUCT.md)に従ってください。

## ターミナルから（任意）

[GitHub CLI](https://cli.github.com) を使えば、同じことをターミナルから実行できます。

```bash
gh pr checkout 123
```

```bash
gh pr review 123 --comment --body "Read the CLI changes; did not run them."
```

```bash
gh pr review 123 --approve --body "Ran bun run test on this branch; looks good."
```

```bash
gh pr review 123 --request-changes --body "The new flag is never passed to the generator (up.ts line 52)."
```

## 承認とマージができる人

- 誰でもコメント、承認、変更依頼ができます。すべてのレビューはメンテナーの判断を速くします。
- 自分の PR を承認することはできません。
- マージするのは[メンテナー](../../../MAINTAINERS.md)だけです。マージ前に、メンテナーはレビューと必須チェックが通っているかを確認します。
