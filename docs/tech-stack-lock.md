# TILT_TECH_STACK.star and version ownership

Despite its name, `TILT_TECH_STACK.star` is not a semantic-version lockfile. It records technology identifiers from the installed Flisk CLI's platform standards. The `v1.0.0` in its generated header is the platform-standards format version, not a version of Bun, Vite, Prisma, or NATS.

A current generated file contains labels such as:

```starlark
{
    "bundler": "vite",
    "runtime": "bun",
    "language": "typescript",
    "orm": "prisma",
    "messaging": "nats",
    "linting": "biome",
    "testing": "vitest",
    "web_framework": "hono",
}
```

These values name tools; they do not include release numbers or image tags.

## What the fields affect

Flisk renders the file from `PLATFORM_STANDARDS.tech` in the CLI and uses it as part of the generated project contract. The values are defined in [platform-standards.ts](../cli/src/config/platform-standards.ts).

| Field | Current value | Current use |
| --- | --- | --- |
| `runtime` | `bun` | The generated Tiltfile checks the selected runtime. `generate_manifest_template` uses it to seed a generated manifest; discovery does not default existing service manifests from it. |
| `bundler` | `vite` | The generated Tiltfile checks the selected bundler. The value does not select a Vite release. |
| `orm` | `prisma` | The generated Tiltfile checks the selected ORM. The value does not select a Prisma package or client release. |
| `messaging` | `nats` | The generated Tiltfile checks the selected messaging tool. `generate_manifest_template` uses it to seed `featuresEnabled`; discovery does not add it as a default feature to existing manifests. The value does not select a NATS image tag. |
| `language` | `typescript` | Exposed as a technology label; it does not pin a TypeScript package version. |
| `web_framework` | `hono` | Exposed as a technology label; it does not pin a Hono package version. |
| `linting` | `biome` | Optional validation warns when a supplied value differs from the standard. This does not pin a Biome package version. |
| `testing` | `vitest` | Optional validation warns when a supplied value differs from the standard. This does not pin a Vitest package version. |

The generated `Tiltfile` passes `runtime`, `bundler`, `orm`, and `messaging` from its `TECH_STACK` map to `assert_tech_stack`. The map and the expected strings are both rendered from the same platform standards, so this only detects when the two generated copies drift (for example, after editing one side); it does not check installed package or image versions. The template also defines optional validation warnings for `linting` and `testing` when a caller supplies values that differ from the standards.

The discovery helper reads `RUNTIME` and `MESSAGING` only in `generate_manifest_template`, where they seed `runtime` and `featuresEnabled` in a generated manifest; `_load_and_normalize` does not apply them as defaults to discovered `service.json` files. `language` and `web_framework` are exported labels only. `PLATFORM_STANDARDS.tech` also contains `database: postgresql`, but the `TILT_TECH_STACK.star` template does not render that property, so it is absent from the generated file. See the [Tiltfile template](../cli/templates/Tiltfile.hbs) and [manifest normalizer](../discovery/manifest/normalize.star) for those consumers. None of the rendered labels represents a package constraint or container tag.

## Where versions live

A resource scaffold, implemented in [resource.ts](../cli/src/commands/resource.ts), writes its own `service.json`, `package.json`, and starter files beneath `services/<stack>/<name>/`. Application dependency constraints belong in that service's `package.json`; the resolved dependency versions belong in its package-manager lockfile. Update those files with the package manager used by the service and commit both. The generated Flisk platform file does not control them.

Runtime images and other generated service files have separate owners. Files under a service's `.autogenerated/` directory are derived from its manifest and Flisk generators; edit the source manifest or use a bring-your-own resource with a Dockerfile or image when you need to own the runtime image. See [bring-your-own resources](byo.md) and [generated files and drift](generated-files.md).

For a service-specific dependency change:

1. Update the dependency in that service's `package.json` using its package manager.
2. Commit the matching lockfile and avoid unpinned values such as `latest` or `*`; see `UNPINNED_DEPENDENCY_VERSIONS` in the [CLI source](../cli/src/utils/constants.ts).
3. Run the service's checks. `flisk config verify` checks the generated project contract and service-file drift; it does not verify dependency versions.

For a service-specific runtime image, use a bring-your-own resource that names your Dockerfile or image. `TILT_TECH_STACK.star` has no per-project image-version field. If the standard scaffold itself needs a different default, that is a Flisk generator change and must be released in the CLI.

## Regenerate and verify

`flisk project` creates the project configuration. `flisk config regenerate` regenerates the master project files from `.tdk/project.json` and the standards bundled with the installed CLI. It does not read version pins from `TILT_TECH_STACK.star`. Editing that generated file does not change a dependency or image version; `flisk config verify` reports the edit as drift, and regeneration restores the generated value.

Regeneration writes project files but does not start Docker, run Tilt, or restart an already running service. The command implementation is in [config.ts](../cli/src/commands/config.ts). Run `flisk up` when you are ready for Tilt to apply project or service changes; affected resources may then be rebuilt or restarted.

`flisk upgrade` upgrades the installed Flisk CLI to the latest release. It does not rewrite a project's service manifests, package dependencies, lockfiles, or images. A later `flisk config regenerate` uses the standards bundled with the upgraded CLI. For the CLI version floor and compatibility notes, see [Upgrading Flisk](upgrading.md).
