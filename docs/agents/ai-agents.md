# Running AI agents in Flisk

Flisk is the local runtime for agent **systems**: your agent process, its local state store, its MCP tool servers, databases, queues, and mock providers, running behind one gateway with one command: `flisk up`.

Instead of running agents as detached scripts or hand-rolling complex Compose files, Flisk gives agents first-class local infrastructure:
- **Durable checkpoints**: Session state survives `flisk down`, container restarts, and hot reload via persistent named volumes.
- **Graceful SIGTERM drains**: In-flight LLM turns checkpoint before shutdown or live-update reloads.
- **Session routing**: Traefik routes requests by session (`x-session-id`), keeping concurrent agent conversations isolated.
- **Liveness and application readiness**: `/health` confirms process liveness. `/ready` verifies the checkpoint store for callers that need to wait before sending turns. Flisk's generated health check uses `healthCheckPath`, which is `/health` in this example.

The product website already publishes a site-level [llms.txt](https://flisk.sh/llms.txt). The files in this folder give agents browsing the source repository a CLI-focused contract.

## Three ways to run or use agents with Flisk

### 1. The first-class `agent` resource type (Recommended)

Scaffold a dedicated agent service with durability and session management:

```bash
flisk resource bot --type agent --stack shop --yes
flisk up shop
```

This creates a Bun HTTP service in `services/shop/bot` with `service.json`:

```json
{
  "$schema": "https://flisk.sh/schemas/service-schema.json",
  "name": "bot",
  "appType": "agent",
  "stack": "shop",
  "port": 4001,
  "healthCheckPath": "/health",
  "agent": {
    "runtime": "custom",
    "durability": "files"
  }
}
```

#### What you get
- **Custom runtime escape hatch**: `src/index.ts` is vendor-neutral (plain Node/Bun built-ins). Call Anthropic, OpenAI, Gemini, LangGraph, or Mastra inside `runTurn(checkpoint, input)`.
- **Files durability volume**: Checkpoints are stored in `/var/lib/flisk-agent/<sessionId>.json` on a named Docker volume (`<project>-<stack>-autogenerated_<res>-agent-state`). The volume survives `flisk down`. Remove it explicitly with `docker volume rm <project>-<stack>-autogenerated_<res>-agent-state`.
- **Session-aware turn execution**: Send a POST to `http://api.shop.localhost/api/bot/turn` with the header `x-session-id: session-123` and the JSON body `{"input": "..."}`. A body without a non-empty string `input` (for example `{"message": "..."}`) gets `400 {"error": "input_required"}` and writes nothing. The agent loads the session checkpoint, appends the user prompt, invokes `runTurn()`, atomically commits the updated checkpoint, and returns the reply.
- **Session list**: `GET http://api.shop.localhost/api/bot/sessions` (no `x-session-id`) returns `{ "sessions": [{ "sessionId", "lastActivity", "status", "checkpointBytes" }], "total": n }`, newest first, at most 500 rows (`total` counts all). `status` is `active` while this instance runs a turn for the session, otherwise `idle`. It reads only checkpoint metadata. `flisk agent sessions <resource>` prints it as a table (`--watch` refreshes, `--json` returns it under `data.sessions`); `--session-id <id>` reads one checkpoint instead. An agent scaffolded before this endpoint answers 404, and the CLI reports `SESSION_LIST_UNSUPPORTED`: copy the `/sessions` handler from a new scaffold into `src/index.ts`.
- **Idle session sweep**: Nothing else reaps a session, so a checkpoint left by a conversation nobody returns to would be kept for the life of the service. A timer drops any session whose last activity is older than `SESSION_IDLE_TIMEOUT_MS` (default 24 h), checked every `SESSION_CLEANUP_INTERVAL_MS` (default 1 h); set either env var on the resource to retune it. A session with a turn in flight is never swept, the sweep stops as soon as the process starts draining, and `DELETE http://api.shop.localhost/api/bot/session` with `x-session-id` drops one session immediately (409 `turn_in_flight` while a turn is running).
- **Application readiness check**: `GET /ready` verifies that the state directory is accessible and writable before callers send turns. It is not the endpoint used by Flisk's generated health check in this example.

### 2. Agent as an `mcp` resource

Expose local tools, databases, and microservices to coding agents (Claude Code, Codex, Cursor) via the Model Context Protocol:

```bash
flisk resource tools-mcp --type mcp --stack shop --yes
flisk up shop
```

- Generates an MCP server built with `@modelcontextprotocol/sdk` on the Streamable HTTP transport at `/mcp`.
- Runs alongside your application services under Traefik routing at `http://api.shop.localhost/api/tools-mcp/mcp`.
- Lets external agents safely query your local database or trigger application endpoints through standardized MCP tools.
- See [docs/mcp.md](../mcp.md) for full details on tool registration and schemas.

---

### 3. Flisk as the control plane via `flisk mcp`

Let your AI coding assistant orchestrate your local stack directly through MCP over stdio:

Configure `flisk mcp` in your agent's MCP settings (e.g., `~/.claude/claude_desktop_config.json` or `.cursor/mcp.json`):

```json
{
  "mcpServers": {
    "flisk": {
      "command": "flisk",
      "args": ["mcp"]
    }
  }
}
```

Now Claude Code, Cursor, or Codex can:
- Run `doctor` to diagnose container runtime or port conflicts.
- Call `up` / `down` to launch or teardown services safely.
- Read structured `status` to verify whether APIs and databases are healthy.
- Inspect `logs` with bounded windows to debug failures without dumping mega-token stack traces into context.
- Create the project and its services with `project_init`, `resource_create` and `stack_assign`, then check the result with `config_verify`.

The setup guide lists every tool: [docs/agent-tooling/flisk-mcp-setup.md](../agent-tooling/flisk-mcp-setup.md#the-tools).

## Agent recipes with existing service types

If you have existing worker pipelines or custom Python/Go agents, you can also host them using standard Flisk primitives:

### Recipe: Python / LangGraph agent as a `worker` with Postgres

For background agents processing task queues or event loops:

```bash
flisk resource research-agent --type worker --stack shop --yes
```

In `service.json`, add dependency links to your database or message queue:

```json
{
  "name": "research-agent",
  "appType": "worker",
  "stack": "shop",
  "dependsOn": ["postgres", "nats"],
  "env": {
    "DATABASE_URL": "@ref(postgres.DATABASE_URL)",
    "NATS_URL": "@ref(nats.NATS_URL)"
  }
}
```

The agent boots only after Postgres and NATS pass their readiness gates, receives clean database credentials, and reconnects smoothly during hot reload.

## How Flisk routes agent traffic

Traefik serves as the unified local gateway for your entire agent topology:

```text
                          +--------------------------+
                          |     Traefik Gateway      |
                          |   (*.localhost:80/8080)  |
                          +----------+---------------+
                                     |
              /api/bot/*             |             /api/tools-mcp/mcp
         (x-session-id sticky)       |                    |
                                     v                    v
                          +----------------+     +----------------+
                          |  agent (bot)   |     |  mcp resource  |
                          | Bun / Lang-    |     |  Tools server  |
                          | Graph / Mastra |     +--------+-------+
                          +--------+-------+              |
                                   |                      |
                                   v                      v
                          +--------------------------------+
                          |  Postgres / NATS / Backend     |
                          +--------------------------------+
```

- **Clean hostnames**: Reach your agents and APIs through `api.<project>.localhost`.
- **Zero port conflicts**: Even with dozens of tools, agents, and backends running, Traefik multiplexes everything through a single host port.

The product website already publishes a site-level [llms.txt](https://flisk.sh/llms.txt).

## Known concurrency issues in the custom agent runtime

The custom agent runtime (generated in `src/index.ts`) is a production-ready template with documented limitations under high concurrency. **These are known bugs that do NOT break typical single-user agent workflows**:

### 1. Race condition: activeTurns counter can lose increments under concurrent POST /turn requests

**Problem**: When multiple simultaneous POST /turn requests arrive for the same `sessionId`, the session counter can become inaccurate.

```javascript
activeTurns.set(sessionId, (activeTurns.get(sessionId) ?? 0) + 1);  // Line 171/355
```

If Request A and Request B both read `activeTurns.get(sessionId)` as 0 before either writes back 1, one increment is lost. The session then appears less busy than it is.

**Impact**: `/sessions` endpoint may incorrectly report a session as `idle` while turns are still in flight. **This is cosmetic for the session list; checkpoints are not affected.**

**Workaround**: Don't rely on the `status: 'active'/'idle'` field for production session management. Use it for UI display only.

### 2. Race condition: activeTurns counter can have inaccurate decrements

The decrement logic has the same issue:
```javascript
const left = (activeTurns.get(sessionId) ?? 1) - 1;  // Line 180/364
if (left > 0) activeTurns.set(sessionId, left);
else activeTurns.delete(sessionId);
```

**Impact**: A session can appear permanently `active` even after all turns complete. Again, cosmetic—the next request for that session will continue to work.

### 3. Race condition: inFlight counter reliability under network errors

The in-flight counter is incremented synchronously but decremented via an async event handler:
```javascript
inFlight++;
res.on('close', () => inFlight--);
```

If a response closes abnormally or the handler doesn't fire reliably, the counter can drift. This affects the drain timeout logic.

**Impact**: Graceful shutdown (`SIGTERM`) might wait longer than `DRAIN_TIMEOUT_MS` (10 seconds) if the counter is out of sync. The process will exit after the timeout, losing any in-flight turns that haven't checkpointed.

**Workaround**: Ensure your `runTurn()` implementation checkpoints frequently, not just at the end of a turn. Flisk calls `store.save()` before sending the reply, so this is handled automatically.

### 4. Drain timeout: In-flight requests are polled every 100ms

The shutdown drain checks every 100ms whether in-flight requests have completed:
```javascript
const timer = setInterval(() => {
  if (inFlight === 0 || Date.now() > deadline) {
    process.exit(0);
  }
}, 100);
```

A request finishing between checks will cause the drain to wait an extra ~100ms before exiting.

**Impact**: Long shutdown times (up to `DRAIN_TIMEOUT_MS + 100ms`) instead of immediate exit.

### 5. Postgres durability: Double close() during shutdown

The postgres version calls `await store.close()` twice during shutdown (lines 223 and 229), which could error on the second call if the first closes the client.

**Impact**: Postgres shutdown logs may show a redundant close error. The process still exits cleanly.

## Fixing these issues (for future releases)

To fix all concurrency issues, the agent runtime should:

1. **Use atomic operations**: Replace the `Map<sessionId, number>` with a more atomic pattern (per-session locks, a Set of active IDs, or request Promise tracking).
2. **Synchronous decrement**: Decrement `inFlight` in a `finally` block or ensure the response handler is reliably called.
3. **Drain waiting**: Use a proper async wait loop instead of polling every 100ms.
4. **Test under load**: Add concurrency tests to verify correctness under 10+ simultaneous requests for the same session.

For now, **the template is safe for**:
- Single-user agent conversations (typical LLM use cases)
- Moderate agent fleets (<100 concurrent sessions)
- Development and testing environments

**If you need bulletproof session isolation and concurrency**:
- Run each user in a dedicated agent instance (container per user, routed by Traefik)
- Offload session state to a SQL database with proper locking (use `agent.durability: "postgres"`)
- Implement per-session mutexes in your `runTurn()` logic if the agent itself is concurrent
