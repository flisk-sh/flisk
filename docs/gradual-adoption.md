# Gradual adoption: some of the team on TDK, the rest not

What happens when TDK is added to a repository that already has its own `package.json`, `Tiltfile`, `.tiltignore`, `docker-compose.yml` and `.gitignore`. Everything here was observed by running `tdk project --yes` in such a repository (a small Node app with Compose), not read from the code. `tdk up` was not run, so port and runtime coexistence is **not checked**.

## What `tdk project --yes` did to that repository

| Existing file | Result |
| --- | --- |
| `package.json`, `Tiltfile`, `.tiltignore`, `docker-compose.yml`, `Dockerfile` | Byte-for-byte unchanged |
| `.gitignore` | Four lines appended: `.env`, `.tdk/.tdk-out/`, `.tdk/.project-id`, `.tdk/smoke/` |

New files that show up in `git status`:

```text
.tdk/project.json
services/platform/database-management/docker-compose.yml
shared-platform-engineering/docker-templates/   (5 shell scripts)
```

New files that are git-ignored: `.env` (generated defaults) and `.tdk/.tdk-out/` (242 files, about 2 MB when re-checked on current `main`: the generated Tiltfile, the vendored engine and the master configs).

Running `tdk project --yes` a second time changed nothing.

TDK starts from its own `Tiltfile` in `.tdk/.tdk-out/`, so a root `Tiltfile` the team already uses is not replaced. Developers who do not use TDK keep running whatever they run today.

## Each service you add

`tdk resource <name> --type bring-your-own --stack <stack> --dockerfile ./Dockerfile` creates `services/<stack>/<name>/` with `service.json`, `AGENTS.md`, `health.conf` and a **placeholder** `Dockerfile` (an nginx stub), not your repository's Dockerfile. To run your own code, point `buildContext` and `dockerfile` in `service.json` at it; see [bring-your-own resources](byo.md). Wiring a real application this way was not tried here.

## What to commit

- Commit: `.tdk/project.json`, each `services/<stack>/<name>/service.json`, and the four `.gitignore` lines.
- Also untracked, not git-ignored, and your call: `shared-platform-engineering/docker-templates/` and `services/platform/database-management/docker-compose.yml`. Whether a teammate's fresh clone regenerates them with `tdk project --yes` was not tested.
- Do not commit `.env` or `.tdk/.tdk-out/`; TDK already ignores them.

## Your own `.tiltignore`

`tdk project` leaves an existing root `.tiltignore` alone. Before this was fixed, `tdk config verify` then failed with `Out of sync: .tiltignore`, so a CI step that ran it failed on every repository that already had one. `tdk config verify` now prints `.tiltignore: not generated by TDK, left as is` and passes. A `.tiltignore` that TDK wrote and someone edited is still reported as drift. `tdk config regenerate` restores such a file (hand edits discarded); `tdk project --yes` leaves it alone, and neither touches one without TDK's header.

## Taking it out again

Run `tdk down` first (`--prune-networks` also removes the project's Docker networks that no container uses; Postgres data stays in its volume, see [local data](data.md#does-it-survive-tdk-down)). Then delete what the list above shows: `.tdk/`, `services/platform/database-management/`, `shared-platform-engineering/docker-templates/`, any `services/<stack>/` you added, `.env`, and the four `.gitignore` lines. [Leaving TDK](leaving-flisk.md) covers what survives, what you lose and what `tdk eject` does.

## Not covered

- Running TDK next to the old Compose stack at the same time (default TDK host ports are in the [FAQ](faq-teams.md#ports-and-running-two-stacks-at-once)).
- Starting one TDK service while its dependencies run elsewhere, such as a shared dev cluster.
