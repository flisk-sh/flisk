# Resource Features & Code Generators

Each TDK service can enable or customize code generators and runtime integrations using the `featuresEnabled: []` array in its `service.json` manifest. These features determine what runtime configuration, client code, and scaffolding TDK writes into that service's `.autogenerated/` directory.

This guide provides the complete catalogue of resource features, explains when to enable or disable them, details the `.autogenerated/` convention and drift protection, and walks through a practical configuration example.

---

## 1. Feature Catalogue

Resource features are defined in [cli/src/utils/resource-features.ts](../cli/src/utils/resource-features.ts) and validated against the [Service JSON Schema](../engine/schemas/service-schema.json). They fall into three categories:

- **Core Generator Features**: Per-service code and client generators that developers enable or disable directly in `featuresEnabled: []`.
- **Core Build Generators**: Foundational runtime files (Dockerfiles, TypeScript configs, Vite configs) that are always generated for applicable resource types.
- **Optional & Premium Features**: Extended capabilities (such as Playwright, DDD path aliases, or Sablier on-demand scaling) that require explicit manifest configuration or license activation.

## 2. When to Enable or Disable Features

### `prisma` (Database ORM & Migrations)
- **Default**: Disabled (`false`).
- **Why it is opt-in**: Enabling Prisma instructs the Starlark build generator to look for a `prisma/schema.prisma` file and include Prisma client dependencies. If `prisma` were enabled by default, every newly scaffolded backend would fail its initial container build on `COPY prisma/` and `test -f prisma/schema.prisma`.
- **When to enable**: Add `"prisma"` to `featuresEnabled` when your backend connects to a database and has a valid `prisma/schema.prisma` schema file.

### `api-client`, `env-config`, and `api-index` (Frontend API Bridge)
- **Default**: Enabled (`true`) for `frontend` resources.
- **What they provide**: These three features work together to automatically inspect the companion backend declared in `backendName` (e.g. `orders-backend`), determine its assigned port and route path, and export a ready-to-use typed client in `.autogenerated/`.
- **When to disable**: Remove them from `featuresEnabled` if your frontend:
  - Uses an external API or third-party GraphQL gateway instead of a local TDK backend.
  - Implements its own custom HTTP client (such as Apollo, TanStack Query, or an Axios instance) and does not need the scaffolded wrapper.

### `playwright` (E2E Testing)
- **Default**: Disabled (`false`).
- **When to enable**: Add `"playwright"` to `featuresEnabled` (or set `"playwright": true` in the manifest) when the service includes Playwright browser tests and needs a generated `playwright.config.ts` pre-wired to the local frontend and backend ports.

### `ddd` (Domain-Driven Design Aliases)
- **Default**: Disabled (`false`) / Premium.
- **When to enable**: If your team organizes backend code into clean DDD tiers (`src/domain`, `src/application`, `src/infrastructure`, `src/presentation`), enabling `"ddd"` generates TypeScript path mappings (`@domain/*`, `@application/*`, `@infrastructure/*`, `@presentation/*`, `@test/*`) in `.autogenerated/tsconfig.autogenerated.json` and configures matching Vite resolve aliases.

### `sablier` (On-Demand Scaling & Deferred Start)
- **Default**: Disabled (`false`) / Premium.
- **When to enable**: In large workspaces with 20+ microservices, running all containers simultaneously consumes substantial RAM. Enabling Sablier via a `sablier: { enable: true }` manifest block stops idle containers after a configurable timeout and wakes them on the next incoming HTTP request. Adding `deferStart: true` skips container creation during `tdk up` entirely until the first request arrives.

## 3. Worked Example: Enabling Prisma on a Backend

Here is a step-by-step example showing how changing `featuresEnabled` drives generation.

### Step 1: Open `service.json`
Consider a backend service located at `services/shop/orders-api/service.json`:

```json
{
  "$schema": "https://flisk-sh.github.io/tdk-landscape.github.io/schema.service.json",
  "schemaVersion": 1,
  "appName": "orders-api",
  "appType": "backend",
  "stack": "shop",
  "port": 4001,
  "healthCheckPath": "/health",
  "dependsOn": ["postgres"],
  "featuresEnabled": []
}
```

### Step 2: Add `"prisma"` to `featuresEnabled`
Edit `featuresEnabled` to include `"prisma"`:

```json
{
  "$schema": "https://flisk-sh.github.io/tdk-landscape.github.io/schema.service.json",
  "schemaVersion": 1,
  "appName": "orders-api",
  "appType": "backend",
  "stack": "shop",
  "port": 4001,
  "healthCheckPath": "/health",
  "dependsOn": ["postgres"],
  "featuresEnabled": [
    "prisma"
  ]
}
```

### Step 3: Run `tdk up` (or `tdk config regenerate`)
Execute `tdk up`:

```bash
tdk up shop
```

TDK evaluates the updated manifest and generates the Prisma configuration:

```
✓ Generated: services/shop/orders-api/.autogenerated/prisma.config.autogenerated.ts
```

### Step 4: Inspect the Generated Output
The generated file at `services/shop/orders-api/.autogenerated/prisma.config.autogenerated.ts` exports the database client wiring and schema location:

```typescript
// SYSTEM-GENERATED by TDK - DO NOT EDIT BY HAND
export const prismaConfig = {
  schemaPath: "prisma/schema.prisma",
  databaseUrl: process.env.DATABASE_URL,
};
```

Tilt automatically incorporates `prisma/` into the container's live-update sync rules and watches the schema for changes.

## 4. The `.autogenerated/` Convention & Drift Gate

Every service directory managed by TDK contains a `.autogenerated/` folder.

```
services/shop/orders-api/
├── .autogenerated/           # System-generated runtime configs (DO NOT EDIT)
│   ├── Dockerfile.app.autogenerated
│   ├── .env.backend.autogenerated
│   ├── tsconfig.autogenerated.json
│   ├── vite.config.backend.autogenerated.ts
│   └── AGENTS.md
├── src/                      # Your application code (EDIT FREELY)
├── package.json
└── service.json              # Declarative manifest (EDIT FREELY)
```

### Why You Must Never Edit `.autogenerated/` Files by Hand
1. **Automatic Overwrites**: TDK regenerates `.autogenerated/` files whenever `service.json`, `.tdk/project.json`, or provider configurations change. Manual edits will be wiped out on the next run.
2. **Drift Gate Protection**: TDK stores contract snapshots in `.autogenerated/.tdk-contract/`. Before launching containers, `tdk up` compares the generated files against their snapshots. If manual edits are detected, startup halts immediately with exit code `2` (`DRIFT_EXIT_CODE`):
   ```
   Generated files were edited by hand and no longer match service.json:
     services/shop/orders-api/.autogenerated/tsconfig.autogenerated.json
   Run `tdk config regenerate` to discard the edits, or bypass with `tdk up --ignore-drift`.
   ```
3. **The Correct Way to Customize**: If a generated file does not meet your needs, adjust the manifest settings (`service.json`), add a build hook, configure a provider option, or use `--type bring-your-own` if you require complete control over the Dockerfile.
