# Flisk Core Topology: Maintainer Guide

This document maps the source code and generation flow in `tdk-cli-core`. It is intended for maintainers changing the CLI, templates, discovery, manifest handling, or Tilt engine. The user-facing model is **Project → Stack → Resource**; the implementation is split between a TypeScript CLI and a Starlark Tilt runtime.

## System overview

```text
Maintainer-owned Flisk source
├── CLI (TypeScript / Bun)
│   ├── project templates (.hbs) ──> project master files
│   └── resource providers/templates ──> starter source files + service.json
├── Discovery (Starlark)
│   └── service.json files ──> normalized resource registry + relationship indexes
└── Engine (Starlark / Tilt)
    ├── per-resource generators ──> .autogenerated/* (including TS config/source)
    ├── manifest adapter ──> service.yaml (Tilt UIResource tracking)
    └── resource orchestration ──> Tilt resources, builds, syncs, dependencies
```

There are two distinct generation stages:

1. **CLI-time scaffolding and project configuration.** The `flisk` executable is TypeScript. It clones a selected project starter or writes resource starter files, and it renders project-level master files from Handlebars templates using `.tdk/project.json` as input.
2. **Tilt-time configuration generation and orchestration.** When Tilt loads the project `Tiltfile`, Starlark discovery reads resource manifests and the Starlark engine generates per-resource configuration under `.autogenerated/`, then declares Tilt resources and their runtime relationships. These files are regenerated from manifests, project config, and source templates; edit the inputs/generator, not generated outputs.

The two stages are connected but not interchangeable: CLI templates establish a project and starter source; the Tilt engine derives runtime/build configuration for the discovered resources.

## The two generation stages in detail

### Stage 1: CLI creates or updates the project inputs

`flisk project` initializes `.tdk/project.json`, a project-level config source. `TemplateEngine` reads that JSON into a generation context and renders Handlebars (`.hbs`) templates. These are **templates**: text files with placeholders and helpers that produce concrete project files. Current master outputs include the project `Tiltfile`, `TILT_TECH_STACK.star`, `TILT_RESOURCE_DEFAULTS.star`, `spec.master`, and `.tiltignore`; config regeneration also manages related generated project assets.

`flisk resource` creates or registers an individual resource. The CLI writes the resource's `service.json`, package metadata, starter source, and test files. Frontend source is supplied by a TypeScript provider in `cli/src/frontend-frameworks/`; backend and worker starters are currently built by TypeScript template functions in the resource command. This is starter code intended for the developer to edit, unlike engine-generated configuration.

The project template is distinct from the **project starter repository** selected by `flisk project <template>`: a starter is cloned from Git, while Handlebars templates render local generated config files.

### Stage 2: Tilt discovers resources and generates runtime configuration

The root `Tiltfile` loads `discovery/` and `engine/topologies/`. Discovery scans configured paths (from `discovery.paths` in `.tdk/project.json` where applicable), loads JSON manifests, validates and normalizes metadata, and builds resource/stack/dependency indexes. The engine consumes that registry to generate runtime/build config, then declares infrastructure and application resources to Tilt.

Most per-resource file generators are Starlark (`.star`) modules in `engine/topologies/tilt/generators/` or `engine/topologies/tilt/resources/orchestrator/generators/`. **Starlark is the generator implementation language here; it is not a template-file extension.** The modules construct output content and write it through Tilt's filesystem helpers. Examples include Vite config, Dockerfiles, local/container TypeScript configs, Prisma config, npm/Bun package-manager config, frontend API helpers, environment config, and generated agent guidance. Outputs generally live under each resource's `.autogenerated/` folder.

Some of these Starlark generators produce **TypeScript files** (`.ts`) or TypeScript project configuration (`.json`). “TypeScript generator” can therefore mean two different things in this repo:

- TypeScript CLI code that writes starter application source or renders project templates.
- Starlark engine code that writes generated TypeScript/config files for each discovered resource.

The output language does not identify the implementation language. For example, a generated `.autogenerated/env.ts` is produced at Tilt-time by a Starlark generator, whereas starter `src/index.ts` is written at CLI-time by TypeScript code.

## Manifest and YAML placement

For application resources, **`service.json` is the developer-authored source of truth** for identity and configuration such as `name`/`appName`, `type`/`appType`, `stack`, path, port, features, and `dependsOn`. Discovery scans and parses JSON manifests; it builds the normalized registry and dependency graph from that data.

`service.yaml` is generated from JSON for Tilt's UIResource/resource tracking and verification paths. It is a downstream representation, not the canonical place to configure a resource. Do not make discovery read YAML as the authoritative resource manifest. If a manifest field or schema changes, update the JSON schema/normalization/validation and the YAML projection as needed.

The repo has more than one YAML concern: `service.yaml` is generated per resource, while YAML files such as `platform/services/platform/proxy/service.yaml` can also be checked-in definitions for platform resources or optional infrastructure. Do not assume every YAML file is a generated application manifest; check the consumer. Compose configuration is also YAML and belongs to infrastructure/runtime configuration, not the application manifest data model.

## Discovery and runtime flow

```text
.tdk/project.json                 service.json per resource
  ├─ project name/features           ├─ resource identity and type
  ├─ discovery.paths                  ├─ stack and startup dependencies
  └─ phase → enabled stack list       └─ framework/features/runtime settings
               │                                   │
               └──────────────┬────────────────────┘
                              ▼
                    discovery/ registry
                    ├─ validates/normalizes manifests
                    ├─ indexes resources by name, path, stack
                    └─ records dependency relationships
                              │
                              ▼
                    engine generation pass
                    ├─ .autogenerated/* files per resource
                    ├─ service.yaml UIResource representation
                    └─ Tilt resource declarations and dependency ordering
                              │
                              ▼
                    Tilt builds, syncs, health checks,
                    routes and starts selected resources
```

Project phases select which stacks are brought up by default; `dependsOn` describes resource startup relationships. These are separate controls: a phase is not a dependency edge, and a stack is not a resource. Flisk also has infrastructure resources (for example proxy and database) alongside application resources; their configuration can originate from project feature settings, checked-in platform definitions, or generated engine configuration.

## Where to make a change

| Change | Likely source of truth |
|---|---|
| Change the files created by `flisk resource` | `cli/src/commands/resource.ts`, starter template functions, or a provider in `cli/src/frontend-frameworks/` |
| Change default project files or `.tdk/project.json`-driven root config | `cli/src/generator/template-engine.ts`, `cli/templates/*.hbs`, project command/config code |
| Add or change a field on a resource manifest | Resource schema, discovery manifest normalization/validation, engine manifest mapping and consumers; update generated YAML projection if the field is represented there |
| Change which resource folders are scanned | `.tdk/project.json` `discovery.paths`, discovery scan/config code, and project config types/defaults |
| Change generated per-resource Docker/Vite/TS/package/env files | Corresponding Starlark generator and its orchestration call in `engine/topologies/tilt/resources/orchestrator/generators/` |
| Change startup order or selected stack behavior | Discovery dependency indexes, project phase handling, and engine resource ordering/declaration |
| Change platform infrastructure | Relevant `engine/topologies/platform/` modules and platform resource definitions |

Generated files are useful for debugging the output, but the source templates, manifest, project config, or generator owns their content. Keep writes idempotent where possible and avoid modifying generated output as a fix: it will be regenerated on a later Tilt/config run.
