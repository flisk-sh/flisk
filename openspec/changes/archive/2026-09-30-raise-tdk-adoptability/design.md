## Context

Flisk CLI 1.x needs stronger operational guarantees before users can rely on generated projects. The brief identifies environment checks that currently miss high-impact failures, unclear `flisk up` process behavior, unsafe regeneration boundaries, ambiguous manifest evolution, and a benchmark fixture that does not demonstrate an end-to-end product workflow. Windows support is explicitly scoped to WSL2 Ubuntu with Docker Desktop integration; native Windows may inspect the CLI version but cannot start a landscape.

The work spans CLI doctor/up/config code, generated project templates, example repositories, CI and documentation. The existing README caveat stays in place until the defined requirements are green on main. The separate Luna scorecard/rubric work and the existing 100-service benchmark are not product implementation targets.

## Goals / Non-Goals

**Goals:**
- Detect and prioritize blockers before users start a landscape.
- Make `flisk up` predictable and non-destructive in force and dry-run modes.
- Limit regeneration to TDK-owned generated files and verify generated output against source configuration.
- Make manifest compatibility explicit and preserve user-owned extension fields.
- Prove a representative API/database/worker/frontend workflow through Traefik in required Ubuntu CI.
- Document and script a reproducible WSL2 Ubuntu path.

**Non-Goals:**
- Recalibrating Luna, editing rating files or scorecards, or changing the separate rating proposal.
- Supporting multiple language runtimes, production Kubernetes, or both native Windows and WSL2 as first-class boot environments.
- Recasting the 100-service fixture bench as an ERP product.
- Claiming Windows landscape boot support from Linux CI alone.

## Decisions

1. **WSL2 Ubuntu is the Windows boot contract.** Detect native Windows before landscape startup. `flisk doctor` exits non-zero with the WSL2 + Docker Desktop integration instruction and a link to `docs/wsl2.md`; `flisk up` refuses by default and points users to doctor. `tdk.exe --version` remains available. `TDK_ALLOW_NATIVE_WINDOWS=1` is an explicitly unsupported escape hatch. This chooses one support story over split native/WSL host behavior.

2. **Doctor reports blockers in actionable priority order.** Evaluate Docker daemon state and Linux-container mode, required Tilt and conditional Bun versions, required port binds, WSL project placement, and platform support. Rank required port conflicts ahead of lower-priority checks so a bound 5432 appears in the first failure block. Print all fixes before status summaries; any failed required check yields exit 1. `/mnt/c` is a warning by default and a failure with `--strict`.

3. **Treat dry-run as a no-side-effect planning path.** Route `flisk up --dry-run` before Docker/Tilt startup and generated-file writes. `--force` finds the process listening on `TILT_PORT` (default 10350), terminates that Tilt process, waits for exit, and proceeds; the behavior is shared with `--quiet`. Restrict termination to the process bound to the configured port rather than killing every Tilt process.

4. **Use explicit generated ownership boundaries.** Generated service artifacts live below `.autogenerated/`; existing TDK-owned project-level Tilt files remain generated. In the implementation PR, inventory the owned files and codify the allowlist, including the root `Tiltfile`, `TILT_*.star`, and `.autogenerated/**` where confirmed TDK-owned. Regeneration only writes that allowlist and leaves all other project files intact. `flisk config verify` recomputes/compares generated output with `service.json` and `.tdk/project.json`, reporting file paths and returning 1 on drift. This gives users a CI command that can enforce the same boundary.

5. **Version the manifest contract and preserve extensions.** `service.json` declares an explicit schema version. Unknown fields are retained through load/edit/regenerate operations and produce a warning. Required-field validation reports a JSON-style path. Patch CLI releases do not change required fields; a breaking schema change requires `flisk config migrate` or a major release with a printed warning. This favors forward compatibility without weakening required-field validation.

6. **Make a real-shaped example the default, keep the bench labeled.** The default example includes one Hono API, Postgres, one worker using NATS if the engine already ships it, otherwise the queue the example stack already boots, one Vite frontend, and Traefik routes for UI and API. Do not add a second broker. A UI or curl request writes a database row that the worker can observe. The large ERP-named service landscape remains a fixture bench and every README/docs mention of its 100-service scale labels it as a fixture.

7. **Make Ubuntu E2E the required gate; WSL smoke is reproducible and honest.** `example-e2e` on Ubuntu runs doctor, starts the example, exercises health and the routed write path, and tears down the stack with an eight-minute budget. Add `scripts/wsl2-smoke.sh` and a short command-oriented `docs/wsl2.md`. There is no WSL runner, so add no WSL CI job; the script and docs provide the WSL smoke path, and Ubuntu `example-e2e` is the required gate.

8. **Gate support copy on merged evidence.** Keep the existing “treat 1.x as 0.x” caveat until requirements 2–5 are green on main, and do not remove it based on the proposal or a branch-only result. Once items 1–6 are green on main, replace it with the exact support and generated-files contract stated in the brief.

## Risks / Trade-offs

- [Port owner discovery and termination differ by host OS] → Reuse platform-aware process utilities, validate the PID/command as Tilt, and test the configured-port path including quiet mode.
- [Generated ownership may not cover every existing project-level Tilt file] → Inventory existing TDK-owned outputs before enforcing the allowlist; test both preservation of user files and detection of changed generated files.
- [Unknown fields could be preserved but accidentally omitted by a code path] → Add round-trip fixtures with extra keys and required-field path assertions.
- [An E2E stack can be flaky or exceed runner limits] → Keep one write path, use health readiness checks, enforce an eight-minute timeout, and always tear down via CI cleanup.
- [GitHub has no WSL runner] → Keep the shell smoke script runnable from clean Ubuntu WSL and use documentation plus the script for WSL validation; require Ubuntu `example-e2e` as the CI gate.
- [An older native-Windows proposal remains in the repository] → This change defines the current product decision but does not rewrite or archive unrelated change history; reconcile/archive proposals through the normal OpenSpec lifecycle when appropriate.

## Migration Plan

1. Implement the native-Windows refusal and ordered doctor checks with focused tests.
2. Implement safe `up --force`/`--dry-run` behavior and tests.
3. Establish generated-path ownership, verification, and schema compatibility tests before changing the example.
4. Add the representative example and required Ubuntu E2E workflow; label the existing ERP benchmark as a fixture.
5. Add WSL2 setup documentation and smoke script; do not add a WSL CI job without a runner. Keep Ubuntu `example-e2e` as the required gate.
6. Confirm requirements 1–6 on main before changing the README status line. If any required behavior fails, retain the caveat and correct the failed area before claiming stability.
